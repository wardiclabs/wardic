# Clock cold start: the Priming tick and a scheduler-free Refresh frame loop in core

An animation that starts the Clock from idle (a **Cold start**) moves on the same painted frame as one that joins a running Clock (a warm start). Every Environment's Clock is now built by one DOM-free core constructor, `makeRefreshFrameClock(source: RefreshFrameSource)`, which on a Cold start delivers a **Priming tick** with `dt = NOMINAL_DT` (1/60 s) at the end of the task that starts it, keeps `dt` nominal until two **Refresh frame** timestamps exist, and never goes through the Effect scheduler. `@wardic/dom`'s `ClockDomLive` passes it `requestAnimationFrame` / `cancelAnimationFrame`.

## Why

Issue #14, measured in the layout lab (Chrome 153 and Firefox 156 on Windows, 2026-09-26/27): a layout run that had to start the Clock held its origin for **3** painted frames (about 50 ms) after the measure pass; a run that joined a ticking Clock held **1**, the minimum (the FLIP's first frame shows the origin). The counts were identical under `?scheduler=microtask` and the default `setTimeout(0)` scheduler (40 of 40 cold runs), so the Effect scheduler was not the cause. The two extra frames were:

1. **Late join.** A layout animation starts inside frame K's gate flush: the measure pass starts the coordinator, whose `Clock.ticks` subscription is the Clock's first. A Refresh frame requested at that point lands in K+1, and the gate's one-frame latency (ADR-0006) paints that tick's writes in K+2. A warm Clock's tick for frame K is already queued behind the gate's flush, so it writes in K and the gate paints it in K+1.
2. **`dt = 0`.** The first tick after an acquire advanced nothing (the acquire resets `lastTime`, and the first frame had nothing to measure against).

## Decisions (grilled against Motion, `motion-dom` @ `16c6122`)

- **The Priming tick (issue decision 1).** On a 0 → 1 acquire the loop waits for `nextMicrotask`, publishes one tick with `NOMINAL_DT`, then runs on Refresh frames. Started inside frame K, the Priming tick runs right after the gate's callback, the coordinator writes its first moved value, and the gate paints it in K+1: the warm timing. Its write requests the gate's next frame *before* the loop requests its own, so the steady order (gate flush, then Clock tick) holds from the first frame. Motion needs no such tick, because its layout flush and its animation update share one batch per rAF; its closest analogue is the layout microtask's manual `update` / `preRender` / `render` flush ([create-projection-node.ts:797-806](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/projection/node/create-projection-node.ts#L797-L806)).
- **`dt` stays nominal until two Refresh frames exist (decision 2).** After an acquire the dt sequence is `[NOMINAL_DT (Priming tick), NOMINAL_DT (first Refresh frame), t₂ − t₁, …]`. Only Refresh frame timestamps ever set `lastTime`; the Priming tick has none (it also leaves the `time` Atom alone). This is Motion's own rule: `wake()` sets `useDefaultElapsed`, so the first batch after waking uses `1000 / 60` even after the layout microtask's flush outside rAF ([batcher.ts:47-49, 67-69, 73-76](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/frameloop/batcher.ts#L47-L76)).
- **The loop never touches the Effect scheduler (decision 3).** It forks with `startImmediately`, reaches the Priming tick through `nextMicrotask` (`Effect.callback` + `queueMicrotask`, ADR-0010's #13 amendment), and runs `Effect.forever(…, { disableYield: true })`, requesting each next Refresh frame inside the current one's callback, after the tick is delivered — as Motion requests its next batch at the end of `processBatch` ([batcher.ts:67-70](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/frameloop/batcher.ts#L67-L70)). Measured before deciding: every core pipeline on the binding's path (`Clock.ticks`, `spring`, `tween`, `keyframes`, `springValues`, `animateValues`) delivers its frame inside the Refresh frame callback; the only per-frame scheduler hop was `forever`'s own `yieldNow`. Timing is therefore the same in browsers (scheduler = `setTimeout(0)`), React Native and the test harness (scheduler = microtask).
- **In core (decision 4).** `makeRefreshFrameClock` and `RefreshFrameSource` (`requestFrame` / `cancelFrame`) are Tier 2 (ADR-0008): Effect-typed, for Environment authors. The Clock is a complete reusable unit, so a canvas or native Environment passes its own Refresh frame source instead of re-implementing the Cold start rules (ADR-0004). `InterpolatorRegistryLive` is the precedent for a shared constructor in core.
- **Kept.** The acquire-time `lastTime` reset, so an idle gap never becomes one dt; `MAX_DT = 0.5` at the consumer boundary (`fromClock`, the coordinator's `step`).

## Considered Options

- **Nominal first dt only** (Motion's batcher delta, literally). Rejected: it removes the `dt = 0` frame but not the late join, so a cold layout run would move on the 3rd painted frame instead of the 2nd.
- **Flush the gate in the same frame.** Rejected by ADR-0006 ("Synchronous flush … Rejected") and ADR-0009 ("Gate owns projection timing … Rejected").
- **Keep the Clock warm** (an `RcRef` `idleTimeToLive`). Rejected: it breaks ADR-0009's "Idle stays zero-cost" and the **Shared source** contract (torn down when the last subscriber leaves), and the first start after an idle gap would still be cold.
- **Measure the first Refresh frame's dt from the Priming tick** (`lastTime = performance.now()` at the Priming tick). Rejected: it subtracts two clocks, and when a rAF timestamp precedes the Priming tick (Chrome stamps rAF with the vsync time; a click just after vsync) the dt clamps to 0 and the frame after the first move repeats. Motion never measures from a moment outside a frame either.
- **Remove the scheduler hop at Cold start only**, keeping `forever`'s per-frame yield. Rejected: in a browser that yield requests every next Refresh frame from a `setTimeout(0)` task after paint, so the Clock can lose a frame under main-thread load that the harness and React Native (microtask scheduler) cannot; before this fix a cold spring in headless Chromium held 3 frames under `setTimeout(0)` and 2 under the microtask scheduler.
- **Keep the Clock in `@wardic/dom`**, or write it DOM-free there and lift it with #16. Rejected: every future Environment would re-implement (and drift from) the Cold start rules; the Clock doesn't depend on the projection engine #16 lifts.

## Consequences

- Every Clock-driven Primitive starts up to 2 Refresh frames sooner from idle. A layout animation moves on the 2nd painted frame after the measure pass, cold or warm (1 held). A `useWardic` spring set from a task moves on the 1st painted frame when cold (0 held) and on the 2nd when warm: the warm case's frame is ADR-0006's latency, as before.
- Retargeting the only running animation interrupts it before the new one subscribes, which releases and re-acquires the Clock, so the retarget is a Cold start and gets a Priming tick. Before this fix that cost 2 frames in mid-motion.
- A known edge, documented rather than guarded: a Clock started from a rAF callback that runs *before* a gate flush already pending in the same frame paints its first value one frame early, then repeats it once while the steady order restores itself. It is still earlier than before.
- The Refresh frame loop costs no Effect-scheduler dispatch per frame (one `setTimeout(0)` task fewer per frame in a browser). `velocityOf`'s `zipWith` keeps one hop per frame of its own; its values are still delivered synchronously, and it is not on the binding's path.
- The loop's `RcRef` captures the context of the Clock Layer's build, so a `Scheduler` (or `Tracer`) merged *beside* `DomLive` never reaches the loop; a test that needs one there feeds it in with `Layer.provideMerge`. The per-subscriber `wardic.clock` span runs in the subscriber's fiber, so a sibling tracer (the layout lab's) still records it.
- The contract is pinned in core's node tests on a `setTimeout`-backed scheduler (`packages/core/test/refresh-frame-clock.test.ts`); painted-frame browser tests read post-paint (`packages/solid/test/clock-cold-start.browser.test.tsx`); the layout lab's `held` column (`heldFrames` · `clock`) and scenario 9 show it by hand.
