# Clock cold start: the Priming tick and a scheduler-free Refresh frame loop in core

An animation that starts the Clock from idle (a **Cold start**) moves on the same painted frame as one that joins a running Clock (a warm start). Every Environment's Clock is now built by one DOM-free core constructor, `makeRefreshFrameClock(source: RefreshFrameSource)`, which on a Cold start delivers a **Priming tick** with `dt = NOMINAL_DT` (1/60 s) at the end of the task that starts it, keeps `dt` nominal until two **Refresh frame** timestamps exist, never goes through the Effect scheduler, and stops the way Motion's frame loop does: at the first Refresh frame that finds no subscriber, so a retarget never restarts it. `@wardic/dom`'s `ClockDomLive` passes it `requestAnimationFrame` / `cancelAnimationFrame`.

## Why

Issue #14, measured in the layout lab (Chrome 153 and Firefox 156 on Windows, 2026-09-26/27): a layout run that had to start the Clock held its origin for **3** painted frames (about 50 ms) after the measure pass; a run that joined a ticking Clock held **1**, the minimum (the FLIP's first frame shows the origin). The counts were identical under `?scheduler=microtask` and the default `setTimeout(0)` scheduler (40 of 40 cold runs), so the Effect scheduler was not the cause. The two extra frames were:

1. **Late join.** A layout animation starts inside frame K's gate flush: the measure pass starts the coordinator, whose `Clock.ticks` subscription is the Clock's first. A Refresh frame requested at that point lands in K+1, and the gate's one-frame latency (ADR-0006) paints that tick's writes in K+2. A warm Clock's tick for frame K is already queued behind the gate's flush, so it writes in K and the gate paints it in K+1.
2. **`dt = 0`.** The first tick after an acquire advanced nothing (the acquire resets `lastTime`, and the first frame had nothing to measure against).

## Decisions (grilled against Motion, `motion-dom` @ `16c6122`)

- **The Priming tick (issue decision 1).** On a 0 → 1 acquire the loop waits for `nextMicrotask`, publishes one tick with `NOMINAL_DT`, then runs on Refresh frames. Started inside frame K, the Priming tick runs right after the gate's callback, the coordinator writes its first moved value, and the gate paints it in K+1: the warm timing. Its write requests the gate's next frame *before* the loop requests its own, so the steady order (gate flush, then Clock tick) holds from the first frame. Motion needs no such tick, because its layout flush and its animation update share one batch per rAF; its closest analogue is the layout microtask's manual `update` / `preRender` / `render` flush ([create-projection-node.ts:797-806](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/projection/node/create-projection-node.ts#L797-L806)).
- **`dt` stays nominal until two Refresh frames exist (decision 2).** After an acquire the dt sequence is `[NOMINAL_DT (Priming tick), NOMINAL_DT (first Refresh frame), t₂ − t₁, …]`. Only Refresh frame timestamps ever set `lastTime`; the Priming tick has none (it also left the `time` Atom alone, until #109 removed it: *Amendment (#109)*). This is Motion's own rule: `wake()` sets `useDefaultElapsed`, so the first batch after waking uses `1000 / 60` even after the layout microtask's flush outside rAF ([batcher.ts:47-49, 67-69, 73-76](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/frameloop/batcher.ts#L47-L76)). (A frame that repeats the previous timestamp is timed by elapsed time: *Amendment (#2)* below.)
- **The loop never touches the Effect scheduler (decision 3).** It forks with `startImmediately`, reaches the Priming tick through `nextMicrotask` (`Effect.callback` + `queueMicrotask`, ADR-0010's #13 amendment), and runs its per-frame loop with `Effect.whileLoop`, which never yields (`Effect.forever` would insert a `yieldNow` per iteration unless given `disableYield`), requesting each next Refresh frame inside the current one's callback, after the tick is delivered — as Motion requests its next batch at the end of `processBatch` ([batcher.ts:67-70](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/frameloop/batcher.ts#L67-L70)). Measured before deciding: every core pipeline on the binding's path (`Clock.ticks`, `spring`, `tween`, `keyframes`, `springValues`, `animateValues`) delivers its frame inside the Refresh frame callback; the only per-frame scheduler hop was `forever`'s own `yieldNow`. Timing is therefore the same in browsers (scheduler = `setTimeout(0)`), React Native and the test harness (scheduler = microtask).
- **In core (decision 4).** `makeRefreshFrameClock` and `RefreshFrameSource` (`requestFrame` / `cancelFrame`) are Tier 2 (ADR-0008): Effect-typed, for Environment authors. The Clock is a complete reusable unit, so a canvas or native Environment passes its own Refresh frame source instead of re-implementing the Cold start rules (ADR-0004). `InterpolatorRegistryLive` is the precedent for a shared constructor in core.
- **The loop stops at the first Refresh frame that finds no subscriber (decision 9, from review).** The last subscriber leaving does not stop the loop; its pending Refresh frame fires, finds nobody, and ends the loop without ticking or requesting another. A subscriber that arrives first joins warm: no Priming tick, and a measured dt. This matters because `useWardic` retargets by interrupting the old animation before starting the new one: with nothing else animating, a Clock that stopped on the last unsubscribe restarted cold on every retarget, and the new animation's Priming tick overwrote the old one's value still waiting in the gate, so one step painted doubled (measured 35.2 px against 17.6 px either side; before the Priming tick, the same restart froze a frame instead). Motion behaves this way: stopping an animation leaves its batcher's `runNextFrame` set and the next batch requested, and `schedule` wakes the loop only `if (!runNextFrame)`, so a stop and a start before that batch are warm ([batcher.ts:67-70, 82-88](https://github.com/motiondivision/motion/blob/16c61222c4166bbef5ff6ab0051192faa79fa8c8/packages/motion-dom/src/frameloop/batcher.ts#L67-L88)). The loop is counted by hand rather than held in an `RcRef`, forked into the Clock Layer's scope under the Layer's build context (so it inherits no subscriber's scheduler or op budget); the scope closing interrupts it and cancels its pending request.
- **Kept.** The `lastTime` reset whenever the loop starts, so an idle gap never becomes one dt; `MAX_DT = 0.5` at the consumer boundary (`fromClock`, the coordinator's `step`).

## Considered Options

- **Nominal first dt only** (Motion's batcher delta, literally). Rejected: it removes the `dt = 0` frame but not the late join, so a cold layout run would move on the 3rd painted frame instead of the 2nd.
- **Flush the gate in the same frame.** Rejected by ADR-0006 ("Synchronous flush … Rejected") and ADR-0009 ("Gate owns projection timing … Rejected").
- **Keep the Clock warm** (an `RcRef` `idleTimeToLive`). Rejected: it breaks ADR-0009's "Idle stays zero-cost" and the **Shared source** contract (torn down when the last subscriber leaves), and the first start after an idle gap would still be cold.
- **Measure the first Refresh frame's dt from the Priming tick** (`lastTime = performance.now()` at the Priming tick). Rejected: it subtracts two clocks, and when a rAF timestamp precedes the Priming tick (Chrome stamps rAF with the vsync time; a click just after vsync) the dt clamps to 0 and the frame after the first move repeats. Motion never measures from a moment outside a frame either.
- **Remove the scheduler hop at Cold start only**, keeping `forever`'s per-frame yield. Rejected: in a browser that yield requests every next Refresh frame from a `setTimeout(0)` task after paint, so the Clock can lose a frame under main-thread load that the harness and React Native (microtask scheduler) cannot; before this fix a cold spring in headless Chromium held 3 frames under `setTimeout(0)` and 2 under the microtask scheduler.
- **Keep the Clock in `@wardic/dom`**, or write it DOM-free there and lift it with #16. Rejected: every future Environment would re-implement (and drift from) the Cold start rules; the Clock doesn't depend on the projection engine #16 lifts.
- **Retarget by starting the new animation before interrupting the old one**, in `useWardic`. Rejected for decision 9: it fixes one binding; presence, drag, core consumers that interrupt and restart a stream, and a future React binding would each need the same change.
- **Release the loop at the end of the task in which the last subscriber left.** Rejected for decision 9: it covers an interrupt and a restart in one task, but not a gap across tasks within a frame, and it departs from Motion.

## Consequences

- Every Clock-driven Primitive starts up to 2 Refresh frames sooner from idle. A layout animation moves on the 2nd painted frame after the measure pass, cold or warm (1 held); since *Amendment (#2)* it moves on the 1st painted frame when triggered from a task (0 held) and on the 2nd when triggered after the frame's gate flush (1 held), cold or warm. A `useWardic` spring set from a task moves on the 1st painted frame when cold (0 held) and on the 2nd when warm: the warm case's frame is ADR-0006's latency, as before.
- Retargeting the only running animation keeps the Clock warm (decision 9), so the new animation continues on the next painted frame with a measured dt: no frozen frame (before #14) and no doubled step (the Priming tick without decision 9).
- After the last subscriber leaves, the loop runs one more Refresh frame callback, then stops; idle is otherwise zero-cost (ADR-0009). A subscriber that joins that still-running loop after a long pause in Refresh frames (a hidden tab) gets one large first dt, bounded by `MAX_DT`, exactly as an animation that was running through the pause does.
- A newly mounted layout node that animates on its first measure (a `layoutId` switch's enterer) still hesitates for one frame: the shared `ResizeObserver`'s initial callback schedules a second measure pass, which restarts the node's spring at zero velocity. This predates #14; the old cold start hid it by not moving until the 4th frame. Tracked in #18, resolved by ADR-0018 (a pass leaves a running node whose box didn't change alone).
- A known edge, documented rather than guarded: a Clock started from a rAF callback that runs *before* a gate flush already pending in the same frame paints its first value one frame early, then repeats it once while the steady order restores itself. It is still earlier than before.
- The Refresh frame loop costs no Effect-scheduler dispatch per frame (one `setTimeout(0)` task fewer per frame in a browser). `velocityOf`'s `zipWith` keeps one hop per frame of its own; its values are still delivered synchronously, and it is not on the binding's path (it was two hops, and late with frames back to back; `Velocity.of` went with #25: *Amendment (#25)*).
- The loop runs under the Clock Layer's build context, so a `Scheduler` (or `Tracer`) merged *beside* `DomLive` never reaches it; a test that needs one there feeds it in with `Layer.provideMerge`. The per-subscriber `wardic.clock` span runs in the subscriber's fiber, so a sibling tracer (the layout lab's) still records it.
- The contract is pinned in core's node tests on a `setTimeout`-backed scheduler (`packages/core/test/refresh-frame-clock.test.ts`); painted-frame browser tests read post-paint (`packages/solid/test/clock-cold-start.browser.test.tsx`, including the lone-animation retarget); the layout lab's `held` column (`heldFrames` · `clock`) and scenario 9 show it by hand.

## Amendment (#2, 2026-09-28): layout's frame math, and repeated timestamps

- **Layout starts no longer begin inside the gate's flush.** The late-join arithmetic in *Why* assumed the measure pass ran inside frame K's gate flush. Since ADR-0018 it runs in a microtask at the end of the task that triggered it, and the pass gives the nodes it seeded a **Priming step** (CONTEXT.md). On a Cold start that step is this ADR's Priming tick; on a ticking Clock the projection engine takes it itself. A layout animation triggered from an ordinary task therefore moves on its 1st painted frame (0 held), and one triggered after the frame's gate flush moves on the 2nd (1 held), cold or warm. A `useWardic` spring is unchanged: 0 held cold, 1 warm. The regression tests `clock-cold-start.browser.test.tsx` S1–S3 now assert the 1st painted frame.
- **Decision 2, amended: a repeated Refresh frame timestamp is timed by elapsed time.** Firefox 156 sometimes runs an extra Refresh frame 7–11 ms after the previous one, right after a click, and passes it the previous frame's timestamp; the dt of 0 left the frame's step at nothing (#18: 6 of 6 warm layout runs that held an extra frame, 0 of 9 that didn't; Chrome never repeated a timestamp in 2,719 frames). Such a frame now advances by the time `now()` says has passed since the previous frame (`RefreshFrameSource.now`, Tier 2, default `performance.now()`), the next frame gets the rest of the interval, and a dt never goes below 0. Every other frame still takes its dt from the timestamps; timing every frame by `performance.now()` (Motion's source) was rejected on measured smoothness (ADR-0018).
- The known edge above (a Clock started from a rAF callback that runs before a pending gate flush) still applies to springs.

## Amendment (#68, 2026-10-08): the Frame loop's subscription, and `MAX_DT`

- **The binding's Cold starts now come through the Frame loop's one subscription** (ADR-0027), not one per animation. The timing is the same:
  - a run added in a task gets the Priming tick at the end of that task;
  - a Retarget keeps the loop subscribed, so it stays warm (decision 9);
  - the loop drops its subscription at the first tick with nothing left, and the Clock idles at its next Refresh frame.
- **Consequences say a large first `dt` after a hidden tab is "bounded by `MAX_DT`". That doesn't hold for `springValues`,** and so for every spring the binding runs: it passes the raw `dt` to `stepSpring` (`multi.ts:202`). #68 keeps that, so the Frames don't change; the fix is #78.
- **Fixed by #78** (ADR-0027, *Amendment (#78)*): `springValuesMachine`'s step clamps `dt` at `MAX_DT` once per tick, as every other Clock consumer does, so the Consequences bullet holds again.

## Amendment (#109, 2026-10-11): the Clock writes no Atom

- **`tick` and the Priming tick publish `dt` alone:** the Clock's `time` and `dt` Atoms go (ADR-0030, decision 12), so a Refresh frame no longer writes two Atoms before it publishes.
- **Decision 2's timing is unchanged,** pinned through `ticks` in `refresh-frame-clock.test.ts` where a test read the Atoms: the Priming tick's nominal `dt`, the first Refresh frame's, then the measured interval; and after a repeated timestamp, the next frame's `dt` from the timestamps, not `now()`.

## Amendment (#52, 2026-10-11): the Refresh frame source is an Environment member, with order rules

ADR-0031 decides it, and #122 lands it.
- **The source is a core service of its own,** `RefreshFrameSource.RefreshFrameSource`, in its own module (ADR-0031, decision 2). `ClockDomLive` provides it beside the Clock, built from the same value, and the flush gate requests its flushes from it. `Clock.layer` builds the Clock from the member, and `Clock.fromRefreshFrames(source)` stays for a source that isn't in the Environment. Decision 4's Tier 2 holds.
- **Decision 1's steady order (the gate's flush, then the Clock's tick) is now the source's contract,** kept by every Environment, not a property of the browser (ADR-0031, decision 4). The contract's two rules: a Refresh frame's callbacks run in the order they were requested, and a callback requested while a frame's callbacks run waits for the next frame. `requestAnimationFrame` keeps both.
- **The known edge in *Consequences* is unchanged:** on DOM the member is `requestAnimationFrame`, so a Clock started from a rAF callback that runs before a pending gate flush still paints its first value one frame early, then repeats it once.

## Amendment (#25, 2026-10-11): `Velocity.of` goes

- **`Velocity.of` (`velocityOf`) is removed,** with no alias, and its test with it. Nothing outside that test called it, and a Physics primitive's velocity is on its Frames (`Frame.Physics`). ADR-0028's *Amendment (#25)* records the removal.
- **The Consequences bullet undercounted it.** `Stream.zipWith` forks both pulls each time it pulls both (`effect/Stream.js:2533-2539`, 4.0.2), so it cost 2 dispatcher tasks per element per frame. With frames back to back, its values came after the frame callback, in a dispatcher task: 0 of 1,000 inside it under the default scheduler (`docs/research/clock-and-scheduler.md`, probes a and d). It also paired values with ticks by position, so a value stream that skipped a tick got an older tick's `dt` (probe d).
