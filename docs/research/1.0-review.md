# Wardic 1.0: the final review (#460)

> **Started:** 2026-10-31 · **Issue:** #460, the last item of the 1.0 parity tracker (#426) ·
> **Decisions:** grilled on #460 (Q1–Q11), posted there.

1.0 adds Motion React's API to both bindings (#427–#443). This review asks whether everything
that added still costs only the elements using it, then audits the Effect 4 and Solid 2 code, and
sweeps what's left. It takes six PRs, each writing its part here:

0. **Upgrade:** Effect, Solid 2 and Solid 1 on their latest releases first.
1. **Measure:** the feature pages, and the whole of 1.0 against `aeece6c`, main before #444.
2. **Cut:** the costs every element pays that come from a feature it doesn't use.
3. **The Effect 4 audit.**
4. **The Solid 2 audit.**
5. **The sweep:** dead code, the ADRs amended during #427–#443, and `until`.

**The bar is "pay for what you use"** (Q2, Q4):
- A cost every element pays, one that uses no new feature included, is cut in Part 2 where it can be.
- A cost that buys a feature for the elements using it is accepted, and named here.
- A feature's cost that grows with the page, not with the elements using it, is fixed or filed.

Every finding ends **fixed** (by which PR), **filed** (#N) or **accepted** (and why).

## Part 0: the upgrade (#503)

Effect 4.0.5 → 4.1.1, Solid 2 rc.19 → rc.20, Solid 1 → 1.9.18, `vite-plugin-solid` → 2.11.15. No
change to Wardic's code was needed. The read and its numbers are
[`effect-4-1-upgrade.md`](effect-4-1-upgrade.md).

| Finding | Ends |
|---|---|
| Effect 4.1.1 calls `AsyncResource#emitDestroy` after each fiber resume: about a third of Node's `ticksOnly` +6–8%. | **Accepted:** Effect's, and in Node and Bun only; a browser has no `process`. |
| Effect's `Context` gained a field, so a context root costs 64 bytes more. Core's Stream workloads make one per element per pull (`Stream.withSpan` on `Clock.ticks` and in `Machine.toStream`). | **Carried to Part 1:** the per-pull context root predates the upgrade. Part 1 carries it to Part 3, with each leg's fiber. |
| rc.20's skills: land a write on its own with `onFlush`, not `queueMicrotask`; hydration runs each adopted compute once with a `Promise` that never settles. | **Carried to Part 4**, the Solid 2 audit. |
| `bench:solid` across the upgrade: Solid 1's unmount −11.8%. | Not attributed; a gain. |
| Found in Part 1: #503 kept `@solidjs/vite-plugin` 3.0.0-next.51 and the routers, as rc.20 meets their peers, but next.51 carries its own rc.18 compiler and `solid-js`, so the Solid 2 examples still compiled on rc.18. `packages/solid`'s compiler, `@solidjs/babel-plugin`, stayed rc.19, so Part 1's Solid 2 numbers are on it. ## Part 1: measure

What ran, on the bench host (local; CI is off for billing), in Chromium but for `bench:core`'s Bun
and Node:
- **The whole of 1.0** (Q2): `bench:solid --base aeece6c --features` and `bench:core --base aeece6c`,
  twice each, beside an A/A run of each against `main` for the noise floor. `aeece6c` is `main`
  before #444, the first parity merge.
- **The feature pages** (Q3, #457): `bench:solid --features` adds a page per feature, every element
  using it. Each is gated head against base when the base has the feature, and reports the
  feature's cost against its reference page: the bench's `wardic.div` page, or for `tapped()` the
  plain wards.
- **A walk of every merge** since `aeece6c` that touched `packages/*/src` (38), each built and
  measured on its own, both bindings: bytes per element per round (six samples), retained memory at
  rest (exact to 0.01 KB, so one), and the warm tasks (two pages).
- **V8's sampling heap profiler** (#452's probe) on the bench's Solid 1 page at `aeece6c`, at
  `ebecdb6` (#502, the last parity merge, before the upgrade), at `main`, and on each side of the
  larger bytes steps, each byte put on its function and on the nearest binding frame.
- **Put back on `main`:** the named suspects (Q2) and the walk's larger retained steps, each
  returned to its old form and measured against `main`.

### The feature pages

`bench:solid --features` (#457): the bench's page, every element using one feature on both its
legs, its values new at every target. None is in `aeece6c`, so each is measured against its
reference page, paired per rep; three runs (the two against `aeece6c` and the A/A), rounded, a range
where they differ:

| Page | mount | Retarget | at-rest Retarget | unmount | bytes |
|---|---|---|---|---|---|
| **Keyframes** (#429), three stops on both keys, Solid 1 | +21% | +38–39% | +41% | +1% | +30% |
| Solid 2 | +20–22% | +36–40% | +43–44% | −11 to −13% | +29–30% |
| **Measured pairs** (#430), `height` from `0` to `auto`, then `50%`, Solid 1 | +23–26% | +67–69% | +51–53% | +38–40% | +45% |
| Solid 2 | +24–26% | +60–62% | +54% | +28–30% | +46% |
| **`transitionEnd`** (#428), `pointer-events` set as its legs land, Solid 1 | +23–24% | +49–51% | +54–55% | +37–39% | +28% |
| Solid 2 | +13–15% | +45–52% | +59–61% | +27–29% | +28–29% |
| **wards** (Solid 2) against `wardic.div` | −11 to −13% | 0 to −1% | −2% | −5 to −7% | −1 to −2% |
| **`tapped()`** (#427, Solid 2) against wards | +52–54% | ±1% | +2–3% | +191–195% | +21–22% |

- **Each buys its feature**, for the elements using it: Keyframes run three stops on every key,
  replayed at every Retarget; a Measured pair adds a key and reads both its ends in px at every
  target.
- **The unmount looks per key**: the two pages that leave a third key on each element (`height`,
  `pointer-events`) pay +27–40% on it, and Keyframes, on the reference's two keys, none.
- **`transitionEnd` costs its Retarget half again**, more than Keyframes' three stops, for a style
  written as the legs land. It's the path #447's checks are on (above), so Part 2 looks at both.
- **Wards are cheaper than `wardic.div`**, as expected: no component between them and the element.
  Against `aeece6c` they grew as the bench's page did: mount +10%, Retarget +12–15%, bytes +6.9%.
- **`tapped()`** opens the press, so its page is the press's cost (Findings).

### Core

`bench:core --base aeece6c`, twice, and A/A against `main`: core's machines alone, 1,000 elements,
each workload as a Stream and as a loop (`Machine.start()`'s step, the form the bindings run per
frame).
- **Bun:** no workload past the A/A run's spread (±7% on the loops, whose frames are 0.1–0.9 ms).
- **Node:** the noise control, `ticksOnly`, +6.6% and +6.4%, and every Stream workload 0.13 MB per
  frame more: Effect 4.1.1's, Part 0's two findings. The loops are flat, their bytes too.
- **Chromium:** the Stream workloads within ±2.3%. `animateValues/loop` failed its gate in both runs,
  +6.7% and +11.4%, as 0.22 → 0.24 ms; at 4,000 elements, where a step of the timer is a smaller
  part of a frame, it's −2.3% [−9.8% – +1.2%].
- **`keyframesValues`** is new (#450), so not gated.

So core's per-frame paths are as fast as before 1.0, and allocate no more. What 1.0 costs every
element is the binding's.
