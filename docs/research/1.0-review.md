# Wardic 1.0: the final review (#460)

> **Started:** 2026-10-31 · **Issue:** #460, the last item of the 1.0 parity tracker (#426) ·
> **Decisions:** grilled on #460 (Q1–Q11), posted there.

1.0 adds Motion React's API to both bindings (#427–#443). This review asks whether everything
that added still costs only the elements using it, then audits the Effect 4 and Solid 2 code, and
sweeps what's left. It takes six PRs, each writing its part here:

0. **Upgrade:** Effect, Solid 2 and Solid 1 on their latest releases first.
1. **Measure:** the feature pages, and the whole of 1.0 against `aeece6c`, main before #444.
2. **Cut:** the costs every element pays that come from a feature it doesn't use.
3. **The Effect 4 audit.**
4. **The Solid 2 audit.**
5. **The sweep:** dead code, the ADRs amended during #427–#443, and `until`.

**The bar is "pay for what you use"** (Q2, Q4):
- A cost every element pays, one that uses no new feature included, is cut in Part 2 where it can be.
- A cost that buys a feature for the elements using it is accepted, and named here.
- A feature's cost that grows with the page, not with the elements using it, is fixed or filed.

Every finding ends **fixed** (by which PR), **filed** (#N) or **accepted** (and why).

## Part 2: cut

Part 1's findings carried here, each cut, filed or accepted. Asked as it began (2026-10-31): the
cuts are **structural**, with Effect's `Bool.and` and `Bool.or` left where they are. A feature's check
is skipped where the element doesn't use it, and a check made per key, per Retarget or per mount
builds nothing, #452's guards. Part 3 grills Q8 again with *`dual`'s cost per call*, below.

### Keyboard press: the keys only while focus is within

ADR-0056 *Amendment (#460)*: Motion's press listens for keys only once its element has focus.
- **`InputSource.focusWithin(target)`,** for an Environment that can say where focus is. With it, a
  press holds its target's focus feed alone at rest, and its keys from a `focus` (its own, or one
  inside it) to the `blur` after, or from the start when focus is already within. Without it, the
  Test Environment's by default, the keys are held throughout, as before. `InputFeed.switched` is the
  subscription the press opens and closes, and a watch's new `onStop` lets it go.
- **One focus listener a window.** The DOM's focus feed was four listeners on each target. It's now
  `focusin` and `focusout` on the target's window, in the capture phase, handed to the targets on
  their path, as its key feed's are. On Solid 1, a keyboard press a blur cancels hands `onTapCancel`
  the `focusout`, where it was the `blur`: the same `FocusEvent`.
- KP9 and KB12 pin it: no key heard before a focus or after the blur, and a press watched once focus
  is already within its element hears the keys at once.

**Solid 1's warm unmount, over the gate, is V8's inlining.** The probe's minified build reproduces
it on every page (+14–16%). With TurboFan's inlining budget raised from 920 to 4,000 bytes of
bytecode, `main`'s warm unmount slows to 6.6 ms as well, and this PR's matches it (−1.5%): `main`'s
5.8 ms is code V8 doesn't inline, and the guards above, smaller functions, tip it over. Among the
inlining decisions that differ, Effect's `setContext` inlines its `makeFiberContextCache` in fewer of
its compiles: 4.1.1's per-fiber context, which Part 1 carried to Part 3. Which line it lands on moves
with any one change. With `startingValuesOf` as a guard (below), the unmount passed (+3.2%) and the
scaled layout frame failed (+5.4%). Accepted for this PR (2026-11-01), and carried to Part 3.

### Tried and left

- **The DOM's `transitionFor`** keeps its `Bool.match`. Each of three other forms, even one that
  only returns early for a key that isn't a transform, made Solid 1's unmount 0.7 ms (12%) slower,
  though `transitionFor` doesn't run in it, and only in the minified bundle: the unminified one, and
  its CPU profile, showed none. So did resolving the base layer alone without `resolvedOf`'s passes.
  Each was bisected to the one change. Taking calls to Effect's shared functions off one hot path
  moves what V8 does with code elsewhere, so both stay, and go to Part 3 with `dual`.
- **`initialOf` and `animateOf`** (#50, #134) keep their matches, two each, called several times a
  mount: as guards they saved 0.9% of the bytes, and made Solid 1's layout frames 6–11% slower (page

### `dual`'s cost per call

Part 1 read `Function.js:77`'s bytes as data-last closures. That line is `dual`'s two-argument wrapper
itself. In Node, one `dual` function called alone, data-first, allocates nothing a call, and ten
different ones called data-first from one function allocate about 54 B a call (536 B a step), where

## Part 3: Effect

The Effect audit (Q6–Q8), in two PRs (split 2026-11-01): this one, 3a, what Effect costs per call on the paths every element takes; 3b, Q7's module state, the Effect 4 skill's checks and the rest of the list.

### `dual`'s cost per call, pinned

Effect's two-argument `dual` is `function (a, b) { if (arguments.length >= 2) return body(a, b); return (self) => body(self, a) }`. The inner closure captures `a`, so V8 gives every call a context for it, a data-first call too, unless TurboFan has inlined the wrapper into an optimized caller and removed it; its other forms read `arguments`, an object in an unoptimized or Maglev caller. Bytes per data-first call, ten different `dual`s on one path (Node):

| Wrapper | TurboFan | Maglev | Ignition |
|---|---|---|---|
| Effect's | 34 | 40 | 40 |
| its data-last closure made by a helper | 5 | 66 | 66 |
| a sentinel default, the closure by a helper | 0 | 0 | 0 |

One `Bool.or`, data-first, is 0 B under TurboFan and 104 B under Maglev, where a binding's per-leg code mostly runs. On the bench page (main, Solid 1), `dual`'s wrapper was 16–18 KB of 138.7 KB per element per round: about 7.5 KB on the per-key, per-Retarget and per-leg path (the binding's Retarget and legs; core's `Machine`, registry, `Values` and Frame loop), 2.5 KB per mount, 1.6 KB inside Effect's own runtime.

### Q8, re-grilled: compose once

Asked with those numbers, the user asked first whether building everything as functional pipelines could keep Effect's utilities without the cost. It can, as definitions. Bytes per call (Node, TurboFan / Maglev):

| The same check, or `map` + `filter` over 4 items | check | pipeline |
|---|---|---|
| piped at the call: `pipe(k, Predicate.or(isSize, …))`, `pipe(xs, Arr.map(f), Arr.filter(g))` | 264 / 472 | 536 / 664 |
| data-first: `Bool.or(isSize(k), …)`, `Arr.filter(Arr.map(xs, f), g)` | 0 / 208 | 264 / 488 |
| composed once at module scope: `const isMeasurable = Predicate.or(isSize, …)`, `flow(Arr.map(f), Arr.filter(g))` | 0 / 0 | 264 / 336 |
| plain `\|\|`, `.map().filter()` | 0 / 0 | 264 / 264 |

The pipeline's 264 B are its two arrays. **Decided: compose once on the hot path** (code run per key or per element on every Retarget, per leg, or per frame): predicates, matchers and pipelines built once at module scope and applied; a step that needs a value only the call has is a statement; Effect's and core's operations data-first. Per mount and below, Q8 as decided, held by lint's `BOOL_OPERANDS` (`Bool.and` / `Bool.or` with a second argument that calls more than a pure check: two found, `LiveValue`'s skip callback and `Machine`'s `inOrder`, both now statements). `effect-first.md`'s *The hot path* and ADR-0025's *Amendment (#460)* hold it.

### Core's own `dual`

Core's 28 operations are built with core's `dual` (`src/internal/dual.ts`, ADR-0028 *Amendment (#460)*): a sentinel default, or a test on the first argument, and the data-last closure made by a helper. A data-first call into core allocates nothing, so a binding calling `Machine.run(m, sink, running)` or `InterpolatorRegistry.withKeyRules(effect, rules)` pays nothing for the form.

### Q6, revised: `fnUntraced`, the span its pipeable

Q6 had a function that wraps itself in a span become `Effect.fn`. `Effect.fn` captures a call-site stack at every call and sets a `CurrentStackFrame`, which ADR-0040 and lint's `SPANS` keep out. Per call (Node, `runSync`): `gen` + `withSpan` 1,950 ns / 3.1 KB; `Effect.fn` 2,600 / 2.3; `fnUntraced` + `withSpan` 1,590 / 2.3; a bare `gen` 810 / 2.1 against `fnUntraced` 300 / 1.4, since `gen` builds its generator closure every call. **Revised (asked 2026-11-01): `fnUntraced` with the same span as its pipeable.** 25 functions moved (core 19, dom 5, test 1); 13 stay, each a gen passed as a value, one run after other work, an inline callback, or `makeRunner`, whose type parameter `fnUntraced` would widen.

### A run's span, only with a tracer

Each leg's run opened a span and provided it as its `ParentSpan`. With no tracer installed, Effect's default records it as a native span nothing reads (attributes, a `BigInt` start time), and the `ParentSpan` gives every leg a new context root, rebuilding its fiber's context cache: the 4.1.1 per-fiber cost Part 1 carried here. Spans feed the devtools, an app's tracer and the tests; a defect is named by the loop from the run's name, not its span. **Decided (asked 2026-11-01): a run opens its span only when a tracer is installed.** Against this PR's head without it: bytes −5.5%, Retarget −13%, rest Retarget −8%, unmount −18%, mount −2%. Keeping the span and dropping only the `ParentSpan` measured −1.6 KB and −2% Retarget.
