## What to read if you only read one thing

**`packages/motion-dom/src/layout/LayoutAnimationBuilder.ts`** — specifically the
module-level comment at lines 33–41 and the function `flushPendingBuilders()`.

This is Motion's *own* answer to the exact question Wardic faces: "how do you run this
engine when you don't have React's commit phase?" It is the implementation behind the
public vanilla API `animateLayout(() => { /* mutate the DOM */ })`
([motion.dev/docs/layout-animations](https://motion.dev/docs/layout-animations): *"Wrap
any layout change with `animateLayout`"*). Its answer is neither a retained measurement
nor a `MutationObserver`: it is an **explicit, caller-supplied mutation callback,
batched on a microtask, with a tree-wide snapshot pass before it and a tree-wide
measure pass after it.**

```ts
/**
 * Builders created within the same synchronous tick are flushed together
 * as a single "commit": every node is snapshotted before any updateDom
 * runs, mirroring React batching renders from different parts of the tree.
 */
let pendingBuilders: LayoutAnimationBuilder[] | undefined
```
— `packages/motion-dom/src/layout/LayoutAnimationBuilder.ts:35-41`

Read it together with its **PR description, [#3748](https://github.com/motiondivision/motion/pull/3748)**,
which is the prose argument for the code (§1a ①) — including the five-step commit pipeline
and the falsifying fixture that only pre-mutation batched snapshots pass.

Second-best read: **`packages/motion-dom/src/projection/node/create-projection-node.ts`
lines 725–815** (`update()` / `didUpdate()`). That ~90 lines *is* the whole commit
lifecycle, and it contains the literal `Write` / `Read ===` / `Write` comment banners
that answer the "tree-wide transform reset" question.

Third: **`.claude/overviews/projection.md`** in the Motion repo — a long-form
architecture + performance write-up, and the surviving descendant of the 751-line
`packages/framer-motion/src/projection/README.md` added by
[PR #3458](https://github.com/motiondivision/motion/pull/3458) (that path now 404s on
`main`; the original is in [`3458.diff`](https://github.com/motiondivision/motion/pull/3458.diff)).
**Provenance caveat:** PR #3458 was merged under the `mattgperry` account but its prose is

### 1a. Ranked: the orchestration/batching sources

**① PR #3748 — "Rewrite animateLayout with batched commits on a shared projection tree"**
· [github.com/motiondivision/motion/pull/3748](https://github.com/motiondivision/motion/pull/3748)
· `mattgperry` · 2026-06-10, merged 2026-06-11 · **⚠️ agent-authored prose**

The single best statement anywhere of *why the whole tree must be batched into one commit*,
and the direct explanation of the `LayoutAnimationBuilder` code in this note's headline
recommendation:

> The headline change is **batched commits**: builders created in the same synchronous tick
> flush together as a single commit —
>
> 1. mount every node across all builders (document order, ancestors first)
> 2. snapshot all of them (`willUpdate`) **before any** `updateDom` runs
> 3. run every builder's `updateDom`
> 4. reconcile additions (all builders), then removals (all builders)
> 5. one shared `root.didUpdate()`, then collect each call's animations into its `GroupAnimation`
>
> This mirrors how React batches renders firing in different parts of the tree into one
> commit, so parallel `animateLayout()` calls on intersecting trees now compose correctly:
> one call's DOM update can no longer corrupt another call's animation origins.

And, crucially, **the falsifying test** — which is the test Wardic should port:

> `parallel-calls-intersecting.html` — call A's update flow-pushes call B's element; only
> pre-mutation batched snapshots give B the correct origin […] Validity check: the first
> two fail against the previous implementation; all 27 pass against this one.

Plus the removal/lead semantics that ADR-0010 needs:

> Removal reconciliation reproduces React/AnimatePresence semantics per `layoutId`:
> - a replacement member added in the same commit → removed node dropped, no crossfade
> - removed lead with a surviving member and a still-connected parent → element restored,
>   relegated, exit crossfade, removed again on `onExitComplete`
> - otherwise dropped → survivor promotes without crossfade

**② PR #3747 — "Rewrite animateLayout on a shared projection tree"**
· [pull/3747](https://github.com/motiondivision/motion/pull/3747) · `mattgperry` · 2026-06-09
· **not merged** (superseded by #3748) · **⚠️ agent-authored**

The predecessor design, and the clearest statement of the microtask-dedupe + shared-tree
requirement:

> Instead of building an ephemeral tree per call, the new version drives the **same**
> projection (FLIP) engine React uses, over plain DOM, through **one shared persistent
> tree**: […] All nodes share the single auto-created root, so calls firing against
> different — or intersecting — parts of the tree collapse their `willUpdate()` snapshots
> into one microtask-deduped `root.didUpdate()` measure pass, exactly how independent React
> renders in different parts of the tree batch into a single commit. A child inside one
> call's scope correctly composes a concurrently-animating parent's transform via the shared
> tree.

> 1. **Mount-before-snapshot** — a node mounting after the update began is flagged
>    layout-dirty and skips its own snapshot, so all nodes are mounted before any
>    `willUpdate()`.

**③ PR #3458 — "Add projection system documentation and type exports"**
· [pull/3458](https://github.com/motiondivision/motion/pull/3458) · `mattgperry` · 2026-01-07,
merged · **⚠️ agent-authored**

Added a 751-line `packages/framer-motion/src/projection/README.md`. **That path 404s on
`main` today** — the document's descendant is the `.claude/overviews/projection.md` I read
in the clone (see §1c). To read the original, use
[`pull/3458.diff`](https://github.com/motiondivision/motion/pull/3458.diff). Its four-phase
listing is the canonical prose statement of the cycle, and note that **the transform reset
appears in both phase 1 and phase 2** — the answer to Wardic's open review item, stated in
words:

> ### Phase 1: Snapshot (`willUpdate()`)
> Called before a layout change is expected:
> - Increments `animationId`
> - **Marks ancestors for transform reset**
> - Takes a `snapshot` of current layout
> - Notifies `"willUpdate"` listeners
>
> ### Phase 2: Layout Measurement (`update()`)
> Called after React renders (via microtask):
> - **Resets transforms on all nodes (`resetTransformStyle`)**
> - Measures new layouts (`updateLayout`)
> - Notifies layout changes (`notifyLayoutUpdate`)
> - Triggers animations if layout changed

And the tree-ordering rationale:

> Sorting ensures parents are processed before children, which is critical for:
> - Correct `treeScale` propagation
> - Parent target resolution before child calculations
> - Proper dirty flag inheritance

**④ PR #1057 — "Changing layout projection from tree traversal to flat array"**
· [pull/1057](https://github.com/motiondivision/motion/pull/1057) · `mattgperry` · 2021-03-23,
merged · **✅ his own words**

The `FlatTree` design decision, and it names the reason as *the coming two-pass traversal*:

> Currently, all `VisualElement`s are kept in a tree structure. Once every frame, layout
> projection calculations are updated by iterating from the top `VisualElement` of every
> tree. This kind of traversal is costly as it can involve many nested loops as the depth of
> the tree increases.
>
> This PR changes the layout tree data structure to be a flat array. **Only**
> `VisualElement`s that have layout projection enabled are added to this array. The array is
> resorted by `VisualElement.depth` when an iteration is triggered and a `VisualElement` has
> been added/removed in the meantime.
>
> Traversing a flat array brings its own performance benefits but this is more crucial with
> the coming changes to relative viewport box resolution, **which will necessitate two-pass
> traversal**.

**⑤ PR #2064 — "`usePaintEffect`"**
· [pull/2064](https://github.com/motiondivision/motion/pull/2064) · `mattgperry` · 2023-04-03
· not merged · **✅ his own words**

Why Motion needs its *own* read/render phase separation rather than React's effects — and
the thrash argument in one sentence:

> The same way `useLayoutEffect` is guaranteed to run post-layout and pre-paint,
> `usePaintEffect` is guaranteed to run post-paint. `useEffect` traditionally runs post-paint
> but in situations where a new render has been triggered by `useLayoutEffect`, [it will run
> synchronously, pre-paint]. The callback provided to `usePaintEffect` runs during the "read"
> phase of the Motion render loop. […] **This way, we can avoid layout thrashing across the
> tree.**

### 1c. First-party docs — the sentences that carry mechanism

[motion.dev/docs/react-layout-animations](https://motion.dev/docs/react-layout-animations):

> Motion measures the layout change, then animates using CSS `transform` (translate + scale)
> instead of actually animating width and height. Animating transforms can entirely avoid
> triggering paint.

> Any layout change that happens as a result of a React render will now be automatically
> animated.

> When performing layout animations, changes to layout should be made via `style` or
> `className`, **not** via animation props like `animate` or `whileHover`, as `layout` will
> take care of the animation.

> Animating `scale` is performant but can distort some styles like `border-radius` and
> `box-shadow`. Motion automatically corrects for scale distortion on these properties, but
> they must be set on the element via `style`.

> Layout animations are blocked during horizontal window resize to improve performance and to
> prevent unnecessary animations.

> When performing a shared layout animation, the transition defined for [the] element we're
> animating **to** will be used.

Documented limits worth copying into Wardic's docs verbatim: `display: inline` never
animates (browsers don't apply `transform`); SVG is unsupported (*"SVGs don't have layout
systems"*); `border` can't render below `1px`, *"which limits the degree of scale correction
that Motion can perform on this style"*.

And the sharpest model contrast, vs View Transitions — useful because it names exactly the
two properties Wardic's projection has and a snapshot-based approach doesn't:

> Whereas Motion animates the elements as they exist on the page, View Transitions API […]
> takes an image snapshot of the previous page state, and crossfades it with a live view of
> the new page state. […] **Doesn't account for scroll**: If the page scroll changes during a
> view transition, elements will incorrectly animate this delta. […] **No relative
> animations**: If a nested element has a `delay` it will get 'left behind' when its parent
> animates away, whereas Motion handles this kind of relative animation.

[motion.dev/docs/react-layout-group](https://motion.dev/docs/react-layout-group) states the
trigger plainly, and confirms the `layoutId` namespace problem:

> `motion` components with a `layout` prop will perform layout animations **every time they
> commit a React render**, or (if set) when their `layoutDependency` prop changes. […]
> `layoutId` is global across your site.

### 1f. The one thing no primary source states

**Nowhere does Matt Perry state, in his own voice, *why* transforms must be reset before
measuring.** The closest primary sources are PR #3458's README phase listing (*"Marks
ancestors for transform reset"* → *"Resets transforms on all nodes"* → *"Measures new
layouts"*, agent-authored) and his #1159 remark about the tree *"using measurements based on
the viewport being in different places"*.

The mechanism is nevertheless **fully determined by the source** (§3c): `getBoundingClientRect`
returns the post-transform rect, so a mid-projection node folds its own and its ancestors'

## 2. The projection node tree

### Creation and parenting

`createProjectionNode(config)`
(`packages/motion-dom/src/projection/node/create-projection-node.ts:140`) is a class
*factory*: it closes over five platform hooks — `attachResizeListener`,
`defaultParent`, `measureScroll`, `checkIsScrollRoot`, `resetTransform` — and returns a
`ProjectionNode` class. Two instantiations exist:

- `HTMLProjectionNode` (`node/HTMLProjectionNode.ts`) — `measureScroll` reads
  `scrollLeft/scrollTop`; `checkIsScrollRoot` is
  `window.getComputedStyle(instance).position === "fixed"`; **`resetTransform` is
  `instance.style.transform = value !== undefined ? value : "none"`**.
- `DocumentProjectionNode` (`node/DocumentProjectionNode.ts`) — mounted on `window`,
  `checkIsScrollRoot: () => true`, and it is the one node that gets an
  `attachResizeListener` (a `window` `resize` listener).

**The root is a lazy singleton, not a provider.** `HTMLProjectionNode`'s `defaultParent`
hook constructs the `DocumentProjectionNode` on first use and caches it in the exported
mutable `rootProjectionNode = { current: undefined }`:

```ts
defaultParent: () => {
    if (!rootProjectionNode.current) {
        const documentNode = new DocumentProjectionNode({})
        documentNode.mount(window)
        documentNode.setOptions({ layoutScroll: true })
        rootProjectionNode.current = documentNode
    }
    return rootProjectionNode.current
},
```
— `node/HTMLProjectionNode.ts`

This is Wardic's *synthetic viewport node* (CONTEXT.md, "Projection node") — same idea,
but Motion reaches it through a module singleton rather than a provider. Note
`layoutScroll: true` on the root: page scroll is always folded in, exactly as ADR-0012
records.

The constructor (`create-projection-node.ts:402-418`) establishes the tree:

```ts
constructor(latestValues = {}, parent = defaultParent?.()) {
    this.latestValues = latestValues
    this.root = parent ? parent.root || parent : this
    this.path = parent ? [...parent.path, parent] : []
    this.parent = parent
    this.depth = parent ? parent.depth + 1 : 0

    for (let i = 0; i < this.path.length; i++) {
        this.path[i].shouldResetTransform = true
    }

    if (this.root === this) this.nodes = new FlatTree()
}
```

Three things worth naming:

1. **`path` is a materialised ancestor chain**, root-first, excluding self. Almost every
   geometry operation walks it (`applyTreeDeltas`, `removeElementScroll`,
   `applyTransform`, `removeTransform`, `measurePageBox`). The projection overview counts
   *"Up to 7 × O(depth) iterations per node per frame"* and flags it as the main
   structural perf debt (`.claude/overviews/projection.md`, "O(depth) Path Iterations" —
   agent-authored, but each row's line citation checks out).
2. **Mere construction dirties every ancestor's transform-reset flag.** A node appearing
   anywhere in the tree means all its ancestors must be measured with transforms off.
   This is the first half of the answer to the tree-wide-reset question.
3. **Only the root owns `nodes: FlatTree`.** There is exactly one flat registry per tree.

`mount(instance)` (`:440`) does the actual registration — and note it is *separate* from
construction:

```ts
this.root.nodes!.add(this)
this.parent && this.parent.children.add(this)

if (this.root.hasTreeAnimated && (layout || layoutId)) {
    this.isLayoutDirty = true
}
...
if (layoutId) {
    this.root.registerSharedNode(layoutId, this)
}
```

`unmount()` (`:608`) reverses it, and for a `layoutId` node calls `this.willUpdate()`
*first* so the leaver's snapshot exists for its replacement.

### `FlatTree` — the ordering primitive

```ts
export class FlatTree {
    private children: WithDepth[] = []
    private isDirty: boolean = false
    add(child)    { addUniqueItem(this.children, child); this.isDirty = true }
    remove(child) { removeItem(this.children, child);   this.isDirty = true }
    forEach(callback) {
        this.isDirty && this.children.sort(compareByDepth)
        this.isDirty = false
        this.children.forEach(callback)
    }
}
```
— `packages/motion-dom/src/projection/utils/flat-tree.ts`, with
`compareByDepth = (a, b) => a.depth - b.depth`
(`packages/motion-dom/src/projection/utils/compare-by-depth.ts`)

This is *the* orchestration data structure. It is a flat, lazily depth-sorted array, not
a recursive walk. It replaced a recursive tree walk in
[PR #1057](https://github.com/motiondivision/motion/pull/1057) (2021, Matt Perry's own
words), and the stated motivation was *not* only speed — *"this is more crucial with the
coming changes to relative viewport box resolution, **which will necessitate two-pass
traversal**"* (§1a ④). Pass separation was designed in, not discovered. Every tree-wide pass in the system is `this.nodes.forEach(fn)` — so
every pass is guaranteed **breadth-ish, parents-before-children, and complete before the
next pass begins**. Motion's own comment on `updateProjection` states why:

```ts
/**
 * This is a multi-step process as shared nodes might be of different depths. Nodes
 * are sorted by depth order, so we need to resolve the entire tree before moving to
 * the next step.
 */
updateProjection = () => { ... }
```
— `create-projection-node.ts:853-858`

### Root / `LayoutGroup` / `layoutRoot` — three different things

These are frequently conflated. In Motion they are orthogonal:

- **Root** — the one `DocumentProjectionNode`. Owns `nodes: FlatTree`,
  `sharedNodes: Map<string, NodeStack>`, `animationId`, `isUpdating`, the update-blocking
  flags. All tree-wide passes are root methods; several carry a literal
  `// Note: currently only running on root node` comment (`:641`, `:724`, `:1851`).
- **`LayoutGroup`** — *not* a tree node at all. It is a `nodeGroup()`
  (`packages/motion-dom/src/projection/node/group.ts`, 37 lines) that only exists to
  **co-dirty** a set of nodes:

  ```ts
  const notify = (node: IProjectionNode) => !node.isLayoutDirty && node.willUpdate(false)
  export function nodeGroup(): NodeGroup {
      const nodes = new Set<IProjectionNode>()
      const dirtyAll = () => nodes.forEach(notify)
      return {
          add: (node) => { nodes.add(node); subscriptions.set(node, node.addEventListener("willUpdate", dirtyAll)) },
          remove: (node) => { nodes.delete(node); subscriptions.get(node)?.(); dirtyAll() },
          dirty: dirtyAll,
      }
  }
  ```

  So: *any* member calling `willUpdate` makes every other member snapshot too
  (`shouldNotifyListeners = false` prevents infinite recursion). That is the whole
  mechanism. On the React side `LayoutGroup` additionally supplies an `id` namespace for
  `layoutId` and a `forceRender` to re-render the subtree
  (`packages/framer-motion/src/components/LayoutGroup/index.tsx`).
- **`layoutRoot`** — a per-node *option* that makes a node a stable reference frame.
  Its orchestration effects, all verified: `willUpdate` recurses into any ancestor with
  `options.layoutRoot` (`:702-704`); `isProjecting()` returns true for it
  unconditionally (`:1361-1368`); a `layoutRoot` relativeParent makes `relativeTarget`
  *persistent* rather than torn down after the animation (`:1600-1605`,
  `:1226-1233` skip the version-invalidation); it forces a layout animation on every
  update (`:543` `this.options.layoutRoot || …`) and runs it instantly
  (`animationOptions.type = false`, `:566-570`), and `setAnimationOrigin` seeds it at
  progress `1000` — i.e. already settled: `this.mixTargetDelta(this.options.layoutRoot ? 1000 : 0)`
  (`:1710`). ADR-0013's reading of `layoutRoot` matches.

## 3. The per-frame measure→commit lifecycle

### 3a. The shared ordered frame loop

`packages/motion-dom/src/frameloop/order.ts` is the entire contract, and its inline
comments name each step's read/write character:

```ts
export const stepsOrder: StepId[] = [
    "setup",            // Compute
    "read",             // Read
    "resolveKeyframes", // Write/Read/Write/Read
    "preUpdate",        // Compute
    "update",           // Compute
    "preRender",        // Compute
    "render",           // Write
    "postRender",       // Compute
] as const
```

`createRenderBatcher(scheduleNextBatch, allowKeepAlive)`
(`frameloop/batcher.ts`) builds a batcher over those steps. **Two instances exist, and
the second one is the key to everything in §7:**

```ts
// frameloop/frame.ts
export const { schedule: frame, cancel: cancelFrame, state: frameData, steps: frameSteps } =
    createRenderBatcher(requestAnimationFrame, true)

// frameloop/microtask.ts
export const { schedule: microtask, cancel: cancelMicrotask } =
    createRenderBatcher(queueMicrotask, false)
```

So `microtask.read(fn)`, `microtask.render(fn)`, `microtask.postRender(fn)` are the same
eight ordered steps, driven by `queueMicrotask` instead of `requestAnimationFrame`, with
keep-alive disabled. Motion has **a microtask-scale frame loop**, and the projection
commit runs on it.

Each step is a `createRenderStep` (`frameloop/render-step.ts`) holding two swapped
`Set<Process>` queues (`thisFrame`/`nextFrame`) to avoid per-frame GC, plus reentrancy
protection: *"If we're already processing we've probably been triggered by a flushSync
inside an existing process. Instead of executing, mark `flushNextFrame` as true and
ensure we flush the following frame at the end of this one."* The `immediate` flag on
`schedule` lets a callback join the currently-processing frame rather than the next.

### 3c. Why the batching is necessary — the three invariants

This is the substance of the question, and the source answers all three explicitly.

#### Invariant 1 — every node snapshots before *any* DOM mutation

`willUpdate` is not "snapshot this node". It is "snapshot this node *and* mark its whole
ancestor path". Two nodes in the same update must both be snapshotted while the DOM still
holds the *old* layout — and DOM mutation is not scoped: changing one element's
`flex-direction` moves its siblings, its cousins, and anything below it in document flow.
There is no way to know, from the mutation, which boxes it invalidated. So the only sound
"before" is *all* boxes, read before *any* write.

Motion enforces this structurally in both bindings:

- **React**: `getSnapshotBeforeUpdate` runs for the entire committing subtree before React
  applies *any* DOM mutation (see §4).
- **Vanilla**: `flushPendingBuilders` collects the union of all targets across all builders
  created in the same tick, mounts them in document order, then runs one snapshot pass, and
  only *then* invokes the user's `updateDom`:

  ```ts
  union.forEach((node) => {
      node.isLayoutDirty = false
      node.willUpdate()
  })

  const updatePromises: Promise<void>[] = []
  for (const builder of builders) {
      const result = builder.runUpdate()          // ← the user's DOM mutation
      if (result) updatePromises.push(result)
  }
  ```
  — `LayoutAnimationBuilder.ts`, `flushPendingBuilders()`

  And the reason the mount pass is separated out, in Motion's words:

  ```
  Discover and mount every node across all builders before snapshotting
  any of them. Mounting during an active update flags isLayoutDirty,
  which would make that node's own willUpdate skip its snapshot.
  Document order guarantees ancestors mount before descendants, even
  when they're discovered by different builders.
  ```

#### Invariant 2 — transforms across the whole tree reset before *any* read, restored after

**This is the direct answer to wardic's open review item, and the claim in
`docs/plans/projection-next-steps.md` is confirmed.** Motion does it, and it does it in
*two* complementary ways depending on which phase you're in.

`getBoundingClientRect()` returns the element's **post-transform viewport rect**. During a
layout animation every animating node carries an inline `transform` — and so does every
*ancestor*. A node's rect is therefore polluted by (a) its own transform and (b) the
composed transform of its entire `path`. A descendant's transform is irrelevant. So the
pollution set is exactly `path + self` — which is precisely the set `willUpdate` flags:

```ts
this.isLayoutDirty = true
for (let i = 0; i < this.path.length; i++) {
    const node = this.path[i]
    node.shouldResetTransform = true
    ...
}
```
— `create-projection-node.ts:687-693`

…plus the constructor's identical loop (`:413-415`), which covers the case of a *newly
created* node under mid-animation ancestors.

**Path A — real DOM reset, in the measure phase.** `root.update()` runs three complete
tree-wide passes, with Motion's own banner comments:

```ts

 * Write
 */

/**
 * Read ==================
 */

this.nodes!.forEach(updateLayout)

/**
 * Write
 */
// Notify listeners that the layout is updated
this.nodes!.forEach(notifyLayoutUpdate)
```
— `create-projection-node.ts:777-789`

`resetTransformStyle(node)` (`:2364`) fires the `BeforeLayoutMeasure` event then calls
`node.resetTransform()` (`:967`):

```ts
        resetTransform(this.instance, transformTemplateValue)   // element.style.transform = "none"
        this.shouldResetTransform = false
        this.scheduleRender()                                  // ← this is the "restore"
    }
}
```

**The restore is not a saved-string write-back — it is a re-render.** `scheduleRender()`
puts `visualElement.render` on `frame.render`, and the reprojected transform is rebuilt
from scratch by `applyProjectionStyles` → `buildProjectionTransform` using the *new*
`projectionDelta`. Because the node's transform is always derived (never authoritative in
the DOM), there is nothing to save. That derivation-not-restoration property is what makes
the reset cheap and correct.

**And crucially, that re-render happens in the same microtask, before paint** — that is
exactly what the manual flush at the tail of `update()` is for:

```ts
/**
 * Manually flush any pending updates. Ideally
 * we could leave this to the following requestAnimationFrame but this seems
 * to leave a flash of incorrectly styled content.
 */
const now = time.now()
frameData.delta = clamp(0, 1000 / 60, now - frameData.timestamp)
frameData.timestamp = now
frameData.isProcessing = true
frameSteps.update.process(frameData)
frameSteps.preRender.process(frameData)
frameSteps.render.process(frameData)
frameData.isProcessing = false
```
— `create-projection-node.ts:794-808`

So the full atomic sequence inside one `microtask.read` callback is:

```
reset all (write) → measure all (read) → compute deltas + start animations (write)
  → flush update → flush preRender (updateProjection) → flush render (reproject all)
```

No paint occurs between the reset and the reprojection. If you split that across a
`requestAnimationFrame`, you get *"a flash of incorrectly styled content"* — Motion's own
words for exactly the bug Wardic would ship.

**Path B — numeric transform removal, in the snapshot phase.** In `willUpdate` Motion
*cannot* reset the DOM: it is (in React) inside `getSnapshotBeforeUpdate`, where writing
is illegal in spirit and useless in practice because the old layout is about to be
destroyed. So the snapshot removes transforms **by calculation** instead. This is why
`measure` takes a flag, and why the two callers pass opposite values:

```ts
measure(removeTransform = true) {
    const pageBox = this.measurePageBox()
    let layoutBox = this.removeElementScroll(pageBox)

    /**
     * Measurements taken during the pre-render stage
     * still have transforms applied so we remove them
     * via calculation.
     */
    if (removeTransform) {
        layoutBox = this.removeTransform(layoutBox)
    }
    roundBox(layoutBox)
    return { animationId: this.root.animationId, measuredBox: pageBox, layoutBox, latestValues: {}, source: this.id }
}
```
— `create-projection-node.ts:999-1022`

- `updateSnapshot()` (`:885`) → `this.measure()` → **`removeTransform = true`** (no DOM
  reset available, subtract numerically).
- `updateLayout()` (`:899`) → `this.measure(false)` → **`removeTransform = false`** (the
  DOM was just reset tree-wide, so the raw rect is already clean).

`removeTransform(box)` (`:1113`) walks `this.path`, and for each ancestor with a transform
calls `removeBoxTransforms(box, node.latestValues, node.snapshot?.layoutBox, sourceBox)` —
and where the ancestor has a *scale* it re-measures on the fly
(`hasScale(node.latestValues) && node.updateSnapshot()`) because unscaling requires knowing
the unscaled origin box.

> **Missing this second mechanism is a distinct bug from missing the first.** Wardic needs
> both, or needs to be sure its snapshot always happens in a phase where a DOM reset is
> possible. See §7.

#### Invariant 3 — why interleaving per-node read/write is wrong, not just slow

Two separate failures, and it is worth keeping them apart:

1. **Correctness.** Reset node A → read A → reproject A → reset B → read B. B is a
   descendant of A. At the moment B is read, A's transform has been *restored*, so B's rect
   is polluted by A's projection. Interleaving doesn't merely thrash; it yields a box in the
   wrong coordinate space. Batching is what makes "measure in an untransformed frame" a
   *frame* rather than a per-node accident. This is why the pass structure is
   `forEach(reset); forEach(read); forEach(write)` and not
   `forEach(node => { reset; read; write })`.
2. **Performance.** `getBoundingClientRect` forces a style/layout recalculation only if
   layout was invalidated since the last one; consecutive reads with no intervening write
   coalesce into one. Interleaving defeats that and makes it N forced layouts. Motion's
   in-repo audit states this precisely — *"All sibling `willUpdate` reads are grouped
   before React's writes (safe — not A/B/A/B thrash), but it's N synchronous forced layouts
   if anything dirtied layout pre-commit"* (`plans/PERFORMANCE_AUDIT.md`, "Projection
   `willUpdate()` does synchronous `getBoundingClientRect` in React commit"). **Provenance:
   agent-authored audit doc; I verified the call chain it cites.**

Motion does knowingly violate its own read/write separation in one narrow place, and
flags it in-code — a useful precedent for how to document such a compromise:

```ts
/**
 * If we're running optimised appear animations then these must be
 * cancelled before measuring the DOM. …
 *
 * Note: This is a DOM write. Worst case scenario is this is sandwiched
 * between other snapshot reads which will cause unnecessary style recalculations.
 * This has to happen here though, as we don't yet know which nodes will need
 * snapshots in startUpdate(), but we only want to cancel optimised animations
 * if a layout animation measurement is actually going to be affected by them.
 */
```
— `create-projection-node.ts:664-678`

#### The fourth reset: `resetSkewAndRotation`

Separate from the transform reset and easy to miss. `startUpdate()` (`:642`) runs
`nodes.forEach(resetSkewAndRotation)` across the whole tree *before* any snapshot:

```ts
startUpdate() {
    if (this.isUpdateBlocked()) return
    this.isUpdating = true
    this.nodes && this.nodes.forEach(resetSkewAndRotation)
    this.animationId++
}
```

`resetSkewAndRotation()` (`:1919`) zeroes `z`, `rotate{,X,Y,Z}`, `skew{X,Y}`, calls
`visualElement.render()` **synchronously**, then restores the values and calls
`scheduleRender()` for the next frame. Its own comment: *"Schedule a render for the next
frame. This ensures we won't visually see the element with the reset rotate value
applied."*

Why it exists: `getBoundingClientRect` on a rotated or skewed element returns the
axis-aligned bounding box of the rotated shape, which is *not* the element's layout box and
cannot be inverted with a translate+scale delta. Translate and scale are removable by
`removeTransform`; rotation and skew are not. So they must be zeroed in the real DOM before
measuring. Note this reset *is* a save-and-restore (`resetDistortingTransform` stashes the
value in a `resetValues` map at `:94-109`), unlike the projection-transform reset.

> **Open question for Wardic:** does the engine handle rotate/skew at measure time at all?
> `hasTransform` in Wardic's `measure.ts` should be checked against Motion's
> (`projection/utils/has-transform.ts`, which includes `rotate`/`skew`/`z`). If Wardic
> measures a rotated layout node, its box is wrong regardless of the tree-reset fix.

### 3d. Update blocking and instant transitions

Three mechanisms, all root-level:

- `blockUpdate()` / `unblockUpdate()` / `updateManuallyBlocked` (`:621-631`) — used by
  `useInstantLayoutTransition()`
  (`packages/framer-motion/src/projection/use-instant-layout-transition.ts`), which sets
  `isUpdating = false; blockUpdate()` then runs the callback. `update()` then takes the
  blocked branch: clear snapshots, clear measurements, no animation.
- `updateBlockedByResize` (`:625`, set in `mount`'s resize listener at `:463-486`) — on a
  window-*width* change Motion blocks updates for 250 ms and finishes all in-flight
  animations, because a resize invalidates every box at once. Note it compares
  `window.innerWidth` specifically, so vertical-only resizes (mobile URL bar) don't
  trigger it. Interesting nuance: while blocked-by-resize it *still* measures
  (`nodes.forEach(forceLayoutMeasure)`) so `onLayoutMeasure` consumers like `Reorder` keep
  working — it only skips `notifyLayoutUpdate`.
- `isTreeAnimationBlocked()` (`:633`) — walks up `parent` checking `isAnimationBlocked`;
  used by drag.

Also `resetTree()` (`:2143`, behind `useResetProjection()`): stop every animation, clear
every measurement, clear `sharedNodes`.

## 4. How the cycle is triggered in React

### It is `getSnapshotBeforeUpdate`, not `useLayoutEffect`

This is the single most important correction to the common mental model, and Motion says
so in a comment explaining why a class component survives in an otherwise hooks codebase:

```tsx
/**
 * If we need to measure the element we load this functionality in a
 * separate class component in order to gain access to getSnapshotBeforeUpdate.
 */
let MeasureLayout: undefined | React.ComponentType<MotionProps>
```
— `packages/framer-motion/src/motion/index.tsx:94-97`

And when a user asked outright when measurement happens, the answer was two words
([issue #1266](https://github.com/motiondivision/motion/issues/1266#issuecomment-977966710)):
*"So in a **`getSnapshotBeforeUpdate`**"*.

`MeasureLayoutWithContext` (`packages/framer-motion/src/motion/features/layout/MeasureLayout.tsx`)
is a `Component` whose `render()` returns `null`. It exists purely as a set of lifecycle
hooks. The mapping is exact:

| React lifecycle | When React runs it | Projection call |
|---|---|---|
| `componentDidMount` | after mount, pre-paint | `layoutGroup.group.add(projection)`; `switchLayoutGroup.register(projection)`; `if (hasTakenAnySnapshot) projection.root.didUpdate()`; set `layoutDependency` + `onExitComplete`; `globalProjectionState.hasEverUpdated = true` |
| **`getSnapshotBeforeUpdate`** | **immediately before React mutates the DOM for this commit, for the whole committing tree** | `projection.isPresent = isPresent`; `projection.willUpdate()`; `promote()` / `relegate()` |
| `componentDidUpdate` | after the DOM is mutated, before paint | `projection.options.layoutAnchor = layoutAnchor`; **`projection.root.didUpdate()`**; `microtask.postRender(() => safeToRemove())` |
| `componentWillUnmount` | on removal | `projection.scheduleCheckAfterUnmount()`; group `remove`; `deregister` |

The pre-mutation half, verbatim:

```tsx
getSnapshotBeforeUpdate(prevProps: MeasureProps) {
    const { layoutDependency, visualElement, drag, isPresent } = this.props
    const { projection } = visualElement
    if (!projection) return null

    projection.isPresent = isPresent

    if (prevProps.layoutDependency !== layoutDependency) {
        projection.setOptions({ ...projection.options, layoutDependency })
    }

    hasTakenAnySnapshot = true

    if (
        drag ||
        prevProps.layoutDependency !== layoutDependency ||
        layoutDependency === undefined ||
        prevProps.isPresent !== isPresent
    ) {
        projection.willUpdate()
    } else {
        this.safeToRemove()
    }
    ...
}
```

Note the gate: **`layoutDependency === undefined` means "snapshot on every render"**, and
supplying a `layoutDependency` is an opt-in memoisation that skips the measure when the
value is unchanged. That is the same trigger Wardic's ADR-0009 lists
("`layoutDependency` (everything else)").

### What React guarantees, precisely

The guarantee Motion leans on is **not** "a hook that runs before my own DOM changes".
It is:

> For a single commit, React runs `getSnapshotBeforeUpdate` on **every** updating class
> component in the committing tree, **before** applying **any** of that commit's DOM
> mutations; then applies all mutations; then runs `componentDidUpdate` on all of them —
> all synchronously, within one task, before the browser paints.

That is a *tree-wide read barrier followed by a tree-wide write barrier*, and it is
precisely Invariant 1 from §3c. `useLayoutEffect` gives you only the *second* boundary
(post-mutation, pre-paint) — which is why Motion uses `useIsomorphicLayoutEffect`
(`packages/framer-motion/src/utils/use-isomorphic-effect.ts`, literally
`isBrowser ? useLayoutEffect : useEffect`) for *value*-spine work like
`visualElement.updateFeatures()` and `visualElement.scheduleRenderMicrotask()`
(`motion/utils/use-visual-element.ts:135-148`), but **not** for the layout snapshot.

Two further scheduling details:

- `didUpdate()` is called by *every* updating node's `componentDidUpdate`, but it
  self-coalesces to one pass via `updateScheduled` (`:811-816`), and `update()` additionally
  guards against a repeat with `if (this.animationId <= this.animationCommitId)` (`:766`).
  So N components → one `microtask.read` → one `update()`.
- `didUpdate` schedules on **`microtask.read`**, not `frame.read`. That is what keeps the
  whole reset/measure/reproject sequence inside the same task as the React commit and ahead
  of paint.

### `safeToRemove` / presence interaction

`MeasureLayout` reads `const [isPresent, safeToRemove] = usePresence()` and threads
`safeToRemove` into three places:

1. `componentDidMount`: `projection.addEventListener("animationComplete", () => this.safeToRemove())`
   and `setOptions({ onExitComplete: () => this.safeToRemove() })`.
2. `getSnapshotBeforeUpdate`: the `else` branch — if nothing dirtied, `safeToRemove()`
   immediately (no layout animation is going to hold the element open).
3. `componentDidUpdate`: `microtask.postRender(() => { if (!projection.currentAnimation && projection.isLead()) this.safeToRemove() })`
   — deliberately *after* the commit's projection pass, so the check sees whether the pass
   actually started an animation.

And on presence loss, the relegation handshake:

```tsx
if (prevProps.isPresent !== isPresent) {
    if (isPresent) {
        projection.promote()
    } else if (!projection.relegate()) {
        /**
         * If there's another stack member taking over from this one,
         * it's in charge of the exit animation and therefore should
         * be in charge of the safe to remove. Otherwise we call it here.
         */
        frame.postRender(() => {
            const stack = projection.getStack()
            if (!stack || !stack.members.length) this.safeToRemove()
        })
    }
}
```

There's a maintainer TODO right above it worth quoting, because it names a real ordering
hazard Wardic will meet too:

```
TODO: We use this data in relegate to determine whether to
promote a previous element. There's no guarantee its presence data
will have updated by this point - if a bug like this arises it will
have to be that we markForRelegation and then find a new lead some other way,
perhaps in didUpdate
```

On unmount, `scheduleCheckAfterUnmount()` (`:831`) defers to `frame.postRender`: if the
node was dirtied, force `root.didUpdate()` so siblings still animate into the gap;
otherwise `checkUpdateFailed()` clears the half-started update's snapshots so a future node
can't resume from stale geometry. Plus the module-level `hasTakenAnySnapshot` latch, whose
comment reads: *"Difficult to capture in a test but to prevent flickering we must set this
to true either on update or unmount. Running `next-env/layout-id` in Safari will show this
behaviour if broken."*

## 5. Shared-element (`layoutId`) lead/follow

### Grouping

Registration is root-level and keyed by string:

```ts

    const stack = this.sharedNodes.get(layoutId)!
    stack.add(node)

    const config = node.options.initialPromotionConfig

    })

```
— `create-projection-node.ts:1851-1869`

Called from `mount()` (`:489-491`). **A new `layoutId` node promotes itself to lead on
mount** — exactly CONTEXT.md's *"the most-recently-mounted live node"*.

`isLead()` / `getLead()` / `getStack()` (`:1871-1889`) are the read side. Note
`isLead()` returns `true` when there is no stack — a plain `layout` node is trivially its
own lead, which is what makes all the `getLead()` calls in the per-frame path
branch-free.

### `NodeStack` — 92 lines, the whole lead/follow model

`packages/motion-dom/src/projection/shared/stack.ts`. Fields: `lead?`, `prevLead?`,
`members: IProjectionNode[]` (mount-ordered array, not a Set).

**`promote(node, preserveFollowOpacity)`** is the interesting one:

```ts
promote(node: IProjectionNode, preserveFollowOpacity?: boolean) {
    const prevLead = this.lead
    if (node === prevLead) return

    this.prevLead = prevLead
    this.lead = node
    node.show()

    if (prevLead) {
        prevLead.updateSnapshot()           // ← the leaver is measured NOW
        node.scheduleRender()

        const { layoutDependency: prevDep } = prevLead.options
        const { layoutDependency: nextDep } = node.options

        if (prevDep === undefined || prevDep !== nextDep) {
            node.resumeFrom = prevLead      // ← the handoff link
            if (preserveFollowOpacity) prevLead.preserveOpacity = true

            if (prevLead.snapshot) {
                node.snapshot = prevLead.snapshot
                node.snapshot.latestValues = prevLead.animationValues || prevLead.latestValues
            }

            if (node.root?.isUpdating) node.isLayoutDirty = true
        }
        if (node.options.crossfade === false) prevLead.hide()
    }
}
```

The mechanism in one line: **the incoming lead adopts the outgoing lead's `snapshot` as
its own**, and records `resumeFrom = prevLead`. Because `Measurements.source` carries the
producing node's id, the incoming node's `snapshot.source !== this.layout.source`, so
`setAnimationOrigin` classifies it as a shared animation (`:1610-1612`). Also note
`snapshot.latestValues` is seeded from the leaver's *animated* values
(`prevLead.animationValues || prevLead.latestValues`), so an interrupted crossfade hands
off mid-flight opacity/radius rather than restarting.

`resumeFrom` → `resumingFrom` is promoted in the `didUpdate` handler:

```ts
if (this.resumeFrom) {
    this.resumingFrom = this.resumeFrom
    this.resumingFrom.resumingFrom = undefined
}
```
— `create-projection-node.ts:551-554`

`resumingFrom` is then the flag that makes the per-frame path treat the node as shared:
`const isShared = Boolean(this.resumingFrom) || this !== lead` — appearing identically in
`resolveTargetDelta` (`:1201`) and `calcProjection` (`:1399`), and passed into
`applyTreeDeltas(box, treeScale, path, isShared)` where it enables the extra
scroll-subtraction and ancestor-`latestValues` transform application branches
(`geometry/delta-apply.ts:110-130`). And in `resolveTargetDelta`, when resuming, the target
is built from the *transformed* layout box rather than the raw one:

```ts

    if (Boolean(this.resumingFrom)) {
        this.applyTransform(this.layout.layoutBox, false, this.target)
    } else {
        copyBoxInto(this.target, this.layout.layoutBox)
    }
    applyBoxDelta(this.target, this.targetDelta)
}
```

**`relegate(node)`** finds a replacement lead by walking *backwards* from the node through
`members`, taking the first one that is both present and DOM-connected:

```ts
relegate(node: IProjectionNode) {
    for (let i = this.members.indexOf(node) - 1; i >= 0; i--) {
        const member = this.members[i]
        if (member.isPresent !== false && (member.instance as HTMLElement)?.isConnected !== false) {
            this.promote(member)
            return true
        }
    }
    return false
}
```

It returns `false` when there is no eligible predecessor — which is exactly the signal
`MeasureLayout.getSnapshotBeforeUpdate` branches on to decide whether *it* owns
`safeToRemove` (§4). `remove(node)` additionally auto-promotes the last member if the lead
itself is being removed. And `add()` opportunistically garbage-collects members whose
instance is disconnected and which hold no snapshot.

### How followers are projected

A follower is *not* separately animated. In `applyProjectionStyles` (`:1991`) every node
in the stack reads `const lead = this.getLead()` and projects into **the lead's** target:

- `applyTransformsToTarget()` (`:1792`) destructures `const { targetWithTransforms, layout, latestValues } = lead` — the follower's `projectionDeltaWithTransform` is computed from *its own* `layoutCorrected` into the *lead's* `targetWithTransforms`. That is how the follower ends up perfectly overlapping the lead, exactly as CONTEXT.md describes.
- `const valuesToRender = lead.animationValues || lead.latestValues` — followers render the lead's mixed values.
- One exception: if `animationType` is position-only (or `preserve-aspect` with a
  >20% aspect-ratio divergence, `shouldAnimatePositionOnly` at `:2451`), a non-lead node
  aligns its box origin to the lead's but keeps its *own* dimensions
  (`applyTransformsToTarget`, `:1801-1818`).
- Followers get `pointerEvents = "none"`: *"This is to ensure that if a follow component
  covers a lead component it doesn't block pointer events on the lead."* (`:2130-2138`).

### The crossfade

Gated in `setAnimationOrigin` (`:1613-1621`):

```ts
const stack = this.getStack()
const isOnlyMember = !stack || stack.members.length <= 1
const shouldCrossfadeOpacity = Boolean(
    isSharedLayoutAnimation &&
        !isOnlyMember &&
        this.options.crossfade === true &&
        !this.path.some(hasOpacityCrossfade)
)
```

Four conditions: it must be a shared animation (different `source`), the twins must
actually coexist, `crossfade` must be on (defaulted to `true` in `setOptions`, `:1150-1157`),
and **no ancestor may already be crossfading** (`hasOpacityCrossfade` at `:2412`, testing
`node.animationValues.opacityExit !== undefined`) — nested crossfades would multiply
opacities.

The blend itself is `mixValues` (`packages/motion-dom/src/projection/animation/mix-values.ts`),
called from inside `mixTargetDelta` each tick:

```ts
if (shouldCrossfadeOpacity) {
    target.opacity     = mixNumber(0, lead.opacity ?? 1,   easeCrossfadeIn(progress))
    target.opacityExit = mixNumber(follow.opacity ?? 1, 0, easeCrossfadeOut(progress))
} else if (isOnlyMember) {
    target.opacity = mixNumber(follow.opacity ?? 1, lead.opacity ?? 1, progress)
}
```

with the two easings **time-compressed into disjoint windows**:

```ts
const easeCrossfadeIn  = compress(0, 0.5, circOut)
const easeCrossfadeOut = compress(0.5, 0.95, noop)

function compress(min, max, easing) {
    return (p) => {
        if (p < min) return 0
        if (p > max) return 1
        return easing(progress(min, max, p))
    }
}
```

So: the **lead fades in over progress 0→0.5 with `circOut`**, and the **follower fades out
over 0.5→0.95 linearly**. That is not a symmetric cross-dissolve — the incoming element is
fully opaque by halfway, and the outgoing one only starts leaving at halfway. (Worth
checking Wardic's ADR-0010 implementation against these exact windows; a symmetric
cross-dissolve reads visibly muddier because both elements are semi-transparent in the
middle.)

`mixValues` also mixes the four corner radii (with a px/percent compatibility check, and
a `Math.max(…, 0)` floor) and `rotate`. Two distinct opacity channels exist —
`opacity` for the lead and `opacityExit` for followers — and `applyProjectionStyles`
selects between them (`:2055-2085`), honouring `preserveOpacity` for a follower that should
keep its own.

`crossfade: false` takes the other path: `promote` calls `prevLead.hide()`, and
`applyProjectionStyles` early-returns `targetStyle.visibility = "hidden"` when
`!this.isVisible` (`:1997-2000`). That is Wardic's **Switch** mode.

`registerSharedNode` reads `node.options.initialPromotionConfig`, which on the React side
comes from `SwitchLayoutGroupContext`
(`packages/framer-motion/src/context/SwitchLayoutGroupContext.ts`):

## 6. Scale correction

### Why it's needed

`buildProjectionTransform` (`packages/motion-dom/src/projection/styles/transform.ts`)
produces, in order: `perspective(…)` → `translate3d(…)` → `scale(1/treeScale)` →
`rotate/rotateX/rotateY/skewX/skewY` → `scale(delta.scale * treeScale)`. Its own comment
on the translate division:

```
The translations we use to calculate are always relative to the viewport coordinate space.
But when we apply scales, we also scale the coordinate space of an element and its children.
For instance if we have a treeScale (the culmination of all parent scales) of 0.5 and we need
to move an element 100 pixels, we actually need to move it 200 in within that scaled space.
```

Because a `scale()` is applied *after* layout and paint, anything the browser computed in
layout units gets multiplied along with the geometry. Geometric distortion of *children* is
handled intrinsically — a child node divides by the inherited `treeScale`. But properties
that are neither geometry nor inherited-through-transform get visibly wrong:

- **`border-radius` in px** — a 10px radius on a box scaled 2× renders as 20px.
- **`box-shadow`** — offset, blur and spread all scale, and under a *non-uniform* scale the
  blur becomes directionally wrong (a circular blur becomes elliptical) — which is why
  Motion has to average.

motion.dev's first-party statement of the problem and the promise:

> *"Because `layout` animations use `transform: scale()`, they can sometimes visually
> distort children or certain CSS properties."* … *"Motion automatically corrects
> distortion on these properties, but they must be set via the `style`, `animate` or other
> animation prop."*
> — [motion.dev/docs/react-layout-animations](https://motion.dev/docs/react-layout-animations)

The listed set is **child elements, border radius, box shadow**.

**And there is a hard limit no registry can cross**, which Wardic should document rather
than chase. Matt Perry, closing
[issue #635](https://github.com/motiondivision/motion/issues/635#issuecomment-660157410) as
working-as-intended:

> *"The box is scaling correctly, but the text is stretched because it's changing the amount
> of the box it occupies. […] This is what we want, because **we can only measure bounding
> boxes, not text**. So the more similar the measured box is to text, the more accurate our
> animation will look."*

He restates it in [#2328](https://github.com/motiondivision/motion/issues/2328) three years
later. Related documented limit: *"`border` can't render smaller than `1px`, which limits the
degree of scale correction that Motion can perform on this style"*
([react-layout-animations](https://motion.dev/docs/react-layout-animations)). Text stretch
and sub-pixel borders are **inherent to box-based projection** — they are not ADR-0011 bugs.

### `filter` — no

**`filter` is NOT scale-corrected.** The registry (below) contains exactly six keys:
`borderRadius`, the four per-corner radii, and `boxShadow`. A grep for
`addScaleCorrector|scaleCorrectors` across the whole repo finds no `filter` registration.
`filter` appears only as a *complex value type*
(`packages/motion-dom/src/value/types/complex/filter.ts`) for ordinary animation. So a
`filter: blur(10px)` on a node under a projection scale *will* be distorted, and Motion
neither corrects it nor documents it as corrected. If Wardic corrects `filter`, that is a
deliberate divergence, not parity.

### The registry

```ts
export const scaleCorrectors: ScaleCorrectorMap = {
    borderRadius: { ...correctBorderRadius, applyTo: [...cornerRadiusProps] },
    borderTopLeftRadius: correctBorderRadius,
    borderTopRightRadius: correctBorderRadius,
    borderBottomLeftRadius: correctBorderRadius,
    borderBottomRightRadius: correctBorderRadius,
    boxShadow: correctBoxShadow,
}

export function addScaleCorrector(correctors: ScaleCorrectorMap) {
    for (const key in correctors) {
        scaleCorrectors[key] = correctors[key]
        if (isCSSVariableName(key)) {
            scaleCorrectors[key].isCSSVariable = true
        }
    }
}
```
— `packages/motion-dom/src/projection/styles/scale-correction.ts` (26 lines)

A mutable module-level object with an additive registration function. Public API:
`export { addScaleCorrector } from "motion-dom"`
(`packages/framer-motion/src/index.ts:93`). Three notable design points:

1. `applyTo` lets one authored key fan out to several CSS keys (`borderRadius` → all four
   corners).
2. `isCSSVariable` is auto-detected from the key name, and such values are written to
   `renderState.vars[key]` (needing `setProperty`) rather than to `style[key]`.
3. The corrector interface is deliberately **narrow** to avoid a circular import:

   ```ts
   export interface ScaleCorrectionNode {
       target?: Box
       treeScale?: Point
       projectionDelta?: Delta
   }
   export type ScaleCorrector = (latest: AnyResolvedKeyframe, node: ScaleCorrectionNode) => AnyResolvedKeyframe
   ```
   — `projection/styles/types.ts`, with the comment *"Minimal interface for projection node
   properties used by scale correctors. This avoids circular dependencies with the full
   `IProjectionNode` interface."*

The registry also feeds `isForcedMotionValue`
(`packages/motion-dom/src/render/utils/is-forced-motion-value.ts`) — on a `layout`/`layoutId`
element, any correctable key *and* `opacity` are forced into MotionValues so the engine
owns them. That is the enforcement behind the docs' *"must be set via the `style`,
`animate` or other animation prop"*.

### The two correctors

**`correctBorderRadius`** — converts px to **percent**, and the comment explains the
non-obvious reason:

```
We always correct borderRadius as a percentage rather than pixels to reduce paints.
For example, if you are projecting a box that is 100px wide with a 10px borderRadius
into a box that is 200px wide with a 20px borderRadius, that is actually a 10%
borderRadius in both states. If we animate between the two in pixels that will trigger
a paint each time. If we animate between the two in percentage we'll avoid a paint.
```

```ts
correct: (latest, node) => {
    if (!node.target) return latest
    if (typeof latest === "string") {
        if (px.test(latest)) latest = parseFloat(latest)
        else return latest            // a percentage is already self-correcting
    }
    const x = pixelsToPercent(latest, node.target.x)
    const y = pixelsToPercent(latest, node.target.y)
    return `${x}% ${y}%`
}
```

Two things: it emits a **two-axis** `X% Y%` radius (so non-uniform scale is handled
exactly, not averaged), and it works off **`node.target`**, not `projectionDelta` —
percent radii resolve against the element's *rendered* box, which under projection is the
target box. Wardic's ADR-0011 records the same px→`radius/scale` intuition; note Motion
does it as a percentage of the target rather than a division by the scale. Worth checking
which Wardic implements — the percentage form is both paint-cheaper and axis-exact.

**`correctBoxShadow`** — works off `projectionDelta` × `treeScale`:

```ts
correct: (latest: string, { treeScale, projectionDelta }) => {
    const original = latest
    const shadow = complex.parse(latest)
    if (shadow.length > 5) return original      // TODO: Doesn't support multiple shadows
    const template = complex.createTransformer(latest)
    const offset = typeof shadow[0] !== "number" ? 1 : 0   // leading color

    const xScale = projectionDelta!.x.scale * treeScale!.x
    const yScale = projectionDelta!.y.scale * treeScale!.y

    ;(shadow[0 + offset] as number) /= xScale   // offset-x
    ;(shadow[1 + offset] as number) /= yScale   // offset-y

    /**
     * Ideally we'd correct x and y scales individually, but because blur and
     * spread apply to both we have to take a scale average and apply that instead.
     */
    const averageScale = mixNumber(xScale, yScale, 0.5)
    if (typeof shadow[2 + offset] === "number") (shadow[2 + offset] as number) /= averageScale  // blur
    if (typeof shadow[3 + offset] === "number") (shadow[3 + offset] as number) /= averageScale  // spread
    return template(shadow)
}
```

Note the **effective scale is `projectionDelta.scale * treeScale`**, i.e. the element's own
projection scale composed with the inherited tree scale — which is exactly the
`elementScaleX` that `buildProjectionTransform` emits as its final `scale()`. And the
documented limitation: a multi-shadow value (`shadow.length > 5`) is returned uncorrected.

### How corrected values get applied

Inside `applyProjectionStyles` (`:2087-2120`), on the render step, per frame:

```ts
for (const key in scaleCorrectors) {
    if (valuesToRender[key] === undefined) continue
    const { correct, applyTo, isCSSVariable } = scaleCorrectors[key]

    /**
     * Only apply scale correction to the value if we have an
     * active projection transform. Otherwise these values become
     * vulnerable to distortion if the element changes size without
     * a corresponding layout animation.
     */
    const corrected = transform === "none" ? valuesToRender[key] : correct(valuesToRender[key], lead)

    if (applyTo) {
        for (let i = 0; i < applyTo.length; i++) targetStyle[applyTo[i]] = corrected
    } else if (isCSSVariable) {
        (this.options.visualElement as HTMLVisualElement).renderState.vars[key] = corrected
    } else {
        targetStyle[key] = corrected
    }
}
```

Four details Wardic should match:

1. It iterates **the registry**, not the element's styles — so the loop cost is
   O(registered correctors), and registering many correctors costs every projected element
   every frame. (The repo's own audit lists a related cost: `correctBoxShadow` runs
   `complex.parse` *and* `complex.createTransformer` — two full parses — per element per
   frame; `plans/PERFORMANCE_AUDIT.md` executive-summary item 4. *Agent-authored; the
   double-parse is visible in the source above.*)
2. The corrector is passed **`lead`**, not `this` — a follower corrects using the lead's
   `target`/`projectionDelta`, consistent with it projecting into the lead's box.
3. Correction is **skipped entirely when `transform === "none"`**, for the stated reason.
4. It writes into `targetStyle`, which is the live `element.style` handed down from
   `renderHTML` — so corrected values are written as ordinary style keys by the same code
   that writes everything else. This matches ADR-0011's "computed upstream so the Renderer
   stays pure", though note Motion's version is coupled *into* the renderer rather than
   upstream of it.

## 7. What this implies for a SolidJS binding with no commit phase

### The invariants, restated as requirements

From §3c, in descending order of how badly violating them breaks:

- **(I1) Tree-wide snapshot before any mutation.** Every node that might move must be
  measured while the DOM still holds the *old* layout.
- **(I2) Tree-wide untransformed frame at measure.** Before any `getBoundingClientRect`,
  every node's transform on the `path + self` of every dirty node must be off; after all
  reads, all transforms reprojected — **with no paint in between**.
- **(I3) Pass-separated, depth-ordered passes.** `forEach(reset)`, `forEach(read)`,
  `forEach(write)` over a depth-sorted flat registry — never per-node interleaving.
- **(I4) No paint between the mutation and the first projected frame.** Otherwise: *"a
  flash of incorrectly styled content"* (`create-projection-node.ts:794-798`).
- **(I5) Rotate/skew zeroed in the real DOM before measuring** (`resetSkewAndRotation`),
  because `getBoundingClientRect` on a rotated element returns an axis-aligned hull.
  (Free for Wardic once I2 exists — see §8.7.)

I2–I5 are all *post-mutation* and therefore reachable in Solid without any commit phase —
they only need a batching boundary *somewhere* after the mutation and before paint. **I1 is
the only one that genuinely requires a pre-mutation hook**, and it is the one ADR-0005's
retained-Measurement model trades away.

### Option A — retained Measurement (ADR-0005's current position)

Keep each node's last settled `layout` and treat it as the "before"; after the DOM
settles, re-measure and FLIP the delta.

**First, the evidence against it — and it is Matt Perry in his own words, in 2019, about
this exact idea.** In [issue #275](https://github.com/motiondivision/motion/issues/275#issuecomment-525295014)
he sketches measuring after the content switch and then retracts it within the same thread:

> *"Sorry I thought about it a little longer and realised **the auto measurements will be off
> as they'll all take place after the content is switched.**"*

That is the retained-Measurement model's failure mode named by the author, and it is why
Motion's very next design step was the pre-mutation snapshot. ADR-0005 should engage with
this sentence directly.

**Second, the evidence for it — and it is also Motion: it uses exactly this, but only as a
narrow fallback, and it says so.**

```ts
/**
 * When a node is animation-blocked (e.g. during drag) and its component
 * didn't re-render (memoized), willUpdate() is never called so there's
 * no snapshot. Use the previous layout as a snapshot and mark dirty so
 * resetTransform/updateLayout/notifyLayoutUpdate process it normally.
 */
function ensureDraggedNodesSnapshotted(node: IProjectionNode) {
    if (node.isAnimationBlocked && node.layout && !node.isLayoutDirty) {
        node.snapshot = node.layout
        node.isLayoutDirty = true
    }
}
```
— `create-projection-node.ts:2351-2362`, called from `update()` at `:772`

`node.snapshot = node.layout` **is** the retained Measurement. So the model is sound
enough for Motion to rely on in production — but note the conditions under which Motion
accepts it: the node is animation-blocked, so it isn't mid-projection, and `layout` is the
last *clean, transform-free* measurement (`measure(false)` after a tree-wide reset).

What it gets wrong, and precisely when:

1. **Stale by one settled state, not by one animation.** `layout` is only refreshed in
   `updateLayout()`, i.e. during a measure pass. If two layout changes land without a
   measure pass between them, the second FLIP's "before" is the box from *two* changes ago.
   Motion's `animationCommitId` guard (`:766`) and Wardic's per-pass measure scope should
   make this rare, but it is the failure mode to test.
2. **Wrong for any layout change Wardic doesn't have a trigger for.** With a pre-mutation
   hook, "something might have changed" is implied by the commit itself. With retained
   Measurements, correctness is bounded by trigger coverage — and ADR-0009's trigger set is
   node registration + `ResizeObserver` + `layoutDependency`. A change in an *untracked*
   sibling that reflows a tracked node (CONTEXT.md's own note that *"a position-only move is
   invisible to `Probe.observeResize`"*) produces no trigger, so the retained Measurement
   silently becomes the new box and the animation is skipped. **This is the real cost, and
   it is a coverage problem, not a timing problem.** Motion's pre-mutation hook is a
   *universal* trigger; nothing else is.

   Motion has a natural experiment for this. When React Compiler memoises a subtree,
   Motion's universal trigger stops firing and the failure is exactly Wardic's structural
   one: *"layout animations don't work with optimized components using the react compiler"*
   ([issue #3416](https://github.com/motiondivision/motion/issues/3416)) — nothing renders,
   so nothing measures, and the prescribed fix is `layoutDependency`. **Wardic's default
   state is Motion's memoised-subtree bug state.** `layoutDependency` is therefore not a
   convenience in Wardic; it is the primary correctness knob, and its ergonomics deserve
   more attention than they would in a React port.
3. **Interrupt during flight.** If a change arrives mid-animation, the retained `layout` is
   the *destination* box of the in-flight animation, not the element's current visual
   position. Motion handles this by re-deriving the origin from the live projected box —
   `setAnimationOrigin` is called *after* `startAnimation` specifically for this: *"Set
   animation origin after starting animation to avoid layout jump caused by stopping
   previous layout animation"* (`:576-580`) — and by `attemptToResolveRelativeTarget`
   (`:1306-1327`). ADR-0009 already records "origin re-derived from the live projected box
   on interrupt", so this is covered.
4. **It cannot fix I2.** Retaining a measurement says nothing about the frame the *new*
   measurement is taken in. Whatever Wardic chooses for the "before", the "after" read still
   needs the tree-wide untransformed frame.

**Verdict: viable, and Motion-sanctioned as a fallback — but only if trigger coverage is
treated as a first-class correctness concern.** The honest framing for ADR-0005 is not
"retained Measurement vs. synchronous snapshot" but "**universal trigger vs. enumerated
triggers**". The retained Measurement is a consequence of the trigger choice, not the
decision itself.

### Option B — a caller-declared mutation boundary (what Motion actually ships for non-React)

`animateLayout(() => { /* mutate */ })`. The caller marks the boundary explicitly; Motion
snapshots before invoking the callback and measures after.

This is a *complete* solution to I1 with no framework support at all, which is why
`LayoutAnimationBuilder` exists. Its full sequence (`flushPendingBuilders`):

```
constructor: push onto pendingBuilders; if first, queueMicrotask(flushPendingBuilders)
  ── microtask ──
  flushPendingFrame()                       // materialise any seeked-but-unrendered state
  collect union of targets across ALL builders in this tick
  mount them in document order (ancestors first)
  union.forEach(node => { node.isLayoutDirty = false; node.willUpdate() })   ← I1
  for (builder of builders) builder.runUpdate()      // the caller's mutation(s)
  [await, if any updateDom returned a promise]
  commit():
    reconcileAdditions for all builders, THEN reconcileRemovals for all
    root.didUpdate()                        // → microtask.read → update() → I2/I3/I4
    microtask.render(() => builders.forEach(finalize))   // collect the started animations
```

Two orchestration lessons beyond I1:

- **Cross-caller batching.** Multiple `animateLayout` calls in the same tick merge into one
  commit. Solid's fine-grained updates make this *more* necessary than in React, not less —
  several unrelated effects can mutate layout in the same microtask.
- **Additions before removals, globally.** *"Process all additions before any removals so
  that, even across builders, a removed member knows whether a replacement with the same
  layoutId was added in this commit."* Directly relevant to ADR-0010's leaving-Follower
  handling.

**Cost:** it is not automatic. The developer must wrap the mutation. In Solid that means
either an explicit `animateLayout`-style API, or wrapping the state write
(`animateLayout(() => setItems(next))`). **What it buys:** exact parity with React on I1,
with no guessing. It is also strictly *additive* — it can sit alongside retained
Measurements as the opt-in high-fidelity path, which is likely the right shape for Wardic:
retained Measurement as the default, an explicit boundary for the cases the triggers can't
see.

### Option C — Solid's own scheduling hooks

Assessed against what Solid actually provides (Solid's scheduling is outside this note's
primary-source scope for Motion, so treat the Solid-side claims as **to be verified against
Solid's source** — flagged as an open question):

- **`createRenderEffect`** runs during the render/update pass, *before* the DOM mutations of
  the same update are applied for effects created later in the tree — but Solid's
  fine-grained model gives **no tree-wide barrier**: effect A can run, mutate, and effect B
  run afterwards within the same batch. That breaks I1 *and* I3: the "before" for B is read
  after A already wrote. This is the structural reason ADR-0005's rejection is correct — not
  that Solid lacks a pre-mutation moment, but that it lacks a pre-mutation moment that is
  *tree-wide and singular*.
- **`onMount` / `createEffect`** are post-mutation. They are exactly the right place for
  I2–I4 (the `didUpdate` role), and useless for I1.
- **`queueMicrotask`** — this is the one Motion itself uses, and it is enough for
  everything post-mutation. Solid's effect queue drains synchronously within the
  batch/task; a microtask scheduled from an effect therefore runs after Solid has finished
  all of that update's DOM writes and before the browser paints. That is the `didUpdate` →
  `microtask.read(update)` hop, one-for-one.
- **Wardic's existing `FlushGate`** already satisfies the `ProjectionSink` interface
  (`{ write, scheduleMeasure }`, per `docs/plans/projection-next-steps.md`). This is the
  right home for the reset/read/write pass; the question is only whether it runs *pass
  separated* rather than per node.

**Verdict:** Solid's hooks give I2–I5 for free via the microtask boundary, and give I1
nothing. Do not try to synthesise a pre-mutation barrier from `createRenderEffect`.

### Option D — `requestAnimationFrame`-batched measure

Defer the measure pass to the next rAF instead of a microtask.

**Motion explicitly rejected this**, in a comment written about exactly this choice:

> *"Manually flush any pending updates. Ideally we could leave this to the following
> `requestAnimationFrame` but this seems to leave a flash of incorrectly styled content."*
> — `create-projection-node.ts:794-798`

A paint happens between the mutation and the next rAF. In that paint the element is in its
*new* layout with no projection transform — i.e. visibly at its destination — and then
snaps back to its origin on the next frame. **This is the single most likely visible bug in
a Solid port, and it is a one-line difference (microtask vs. rAF).** Note Motion pays for
avoiding it: the manual `frameSteps.{update,preRender,render}.process()` flush is a
deliberate synchronous re-entry into the frame loop from inside a microtask.

> **Direct implication:** ADR-0009's *"one Clock-driven projection coordinator does the
> per-tick top-down tree walk"* is right for Cycle B (per-frame projection), and the
> `TestClock` determinism argument for it is sound. But Cycle A — the commit — must **not**
> wait for a Clock tick. Motion runs Cycle A on a microtask and then *synchronously drives
> one Cycle B + Cycle C pass* out of it. Wardic needs the same escape hatch: a way for the
> measure pass to force one projection+render pass immediately rather than awaiting the next
> `Clock.ticks` emission. Whether the current engine does this is worth checking against
> `measurePass`.

### Option E — `MutationObserver` / `ResizeObserver` as triggers

- **`ResizeObserver`** is already in ADR-0009 and is the right tool for size changes. It
  cannot see position-only moves (CONTEXT.md notes this) and it fires *after* layout, so it
  is a trigger, never a snapshot source.
- **`MutationObserver`** fires on a microtask after mutations — so it is strictly
  post-mutation and cannot supply I1's "before". It would be a broader *trigger* (ADR-0009
  already reserves it as "a non-breaking future opt-in"), improving the coverage weakness of
  Option A, at the cost of firing on every attribute/child change in the subtree.
- Motion uses **neither** for layout. The only observer in the projection system is the
  root's `window` `resize` listener, and it is used to *block* updates, not trigger them
  (`create-projection-node.ts:461-487`).

### Which one Motion's invariants actually permit

| Requirement | A: retained | B: explicit boundary | C: Solid hooks | D: rAF | E: observers |
|---|---|---|---|---|---|
| I1 tree-wide pre-mutation snapshot | ✗ (approximates) | ✓ | ✗ | ✗ | ✗ |
| I2 tree-wide untransformed frame | n/a | ✓ | ✓ | ✓ | n/a |
| I3 pass separation | n/a | ✓ | ✓ | ✓ | n/a |
| I4 no paint before first projected frame | n/a | ✓ | ✓ | **✗** | n/a |
| Universal trigger coverage | ✗ | ✓ (per call site) | n/a | n/a | partial |
| No API burden on the user | ✓ | ✗ | ✓ | ✓ | ✓ |

**The permitted shape is A + B on a microtask (C), never D.** Concretely:

1. **Default path (A on C).** Retained Measurement as the "before"; trigger from node
   registration + `ResizeObserver` + `layoutDependency`; the measure pass runs on a
   **microtask** scheduled from the post-mutation effect, and does
   `resetAll → readAll → deltaAll` pass-separated over a depth-sorted flat registry,
   followed by a forced projection+render pass **in the same microtask**.
2. **High-fidelity path (B).** An explicit `animateLayout(() => mutate())`-shaped API that
   takes the pre-mutation snapshot for the whole registered tree, then runs the mutation,
   then routes into the same measure pass. This is what Motion ships for non-React and is
   the only way to get I1 exactly. It also solves ADR-0010's cross-caller
   additions-before-removals ordering.
3. **Never D.** If the measure pass is deferred to `Clock.ticks`/rAF, expect the flash
   Motion documents.

## 8. Actionable implications for Wardic

### 8.1 "Tree-wide transform reset on measure (HIGH)" — **CONFIRMED as a real bug**

`docs/plans/projection-next-steps.md` says:

> `measureLayoutBox` (`@wardic/dom/measure.ts`) still clears only the *node's own* inline
> transform. … Motion resets transforms across the whole tree before measuring, then
> restores.

**Confirmed — and it is worse than the review item states.** Reading
`packages/dom/src/measure.ts` and `packages/dom/src/projection.ts:640-736`:

```ts
export const measureLayoutBox = (el: HTMLElement): Bounds => {
  const saved = el.style.transform
  el.style.transform = ""
  try { const r = el.getBoundingClientRect(); return { … } }
  finally { el.style.transform = saved }
}
```
— `wardic:packages/dom/src/measure.ts`

…called from a **single interleaved loop**:

```ts
const ordered = [...nodes].sort((a, b) => a.depth - b.depth)
for (const node of ordered) {
  const viewportBox = boundsToBox(measureLayoutBox(node.element))   // reset → read → RESTORE
  …
  node.retained = newBox
  …                                                                 // delta + spring seed
}
deriveAll()
```
— `wardic:packages/dom/src/projection.ts:645-736`

So there are **two** defects, and the second is not in the review item:

- **(a) Scope.** Only the node's own transform is cleared; ancestors' remain. (This is what
  the review item says.)
- **(b) Structure.** `measureLayoutBox` **restores the transform in a `finally` before the
  next node is read.** Fixing (a) by walking the path inside `measureLayoutBox` would *not*
  fix the bug: node A (an ancestor) would be reset, read, and restored; then node B (its
  descendant) would be read with A's transform back on. This is exactly Motion's Invariant
  I3, and it means the fix is structural — **the reset must be hoisted out of
  `measureLayoutBox` into its own pass**, not extended inside it.

The depth sort and the `computeTree()`-first ordering are already right, and `deriveAll()`
at the tail is already a separated write pass. The missing piece is splitting the
read loop's two halves.

**Two corrections to the "then restores" framing:**

1. **The reset set is `path + self` of every dirty node, not literally "the whole tree".**
   Motion's mechanism is `shouldResetTransform = true` on every entry of `this.path`
   (`create-projection-node.ts:687-693` in `willUpdate`, and identically at `:413-415` in the
   constructor), combined with `isLayoutDirty` on the nodes being measured. `resetTransform()`
   (`:967`) then no-ops for a node that is neither flagged nor actually transformed. This is
   more precise *and* cheaper than a blanket reset — descendant transforms cannot pollute an
   ancestor's `getBoundingClientRect`. Because the pass runs over the depth-sorted `FlatTree`,
   the effect is still "all resets before all reads".
2. **"Then restores" is not a write-back.** The reset calls `this.scheduleRender()`, and the
   transform is *re-derived* from the new `projectionDelta` on the render step. What makes
   this invisible is that the render step is flushed **synchronously at the end of the same
   `update()`**, inside the same microtask, before paint (`:794-808`). If Wardic adds the
   reset but lets the re-render wait for the next Clock tick, it will trade a wrong-box bug
   for a flash bug.

**Good news: Wardic only needs Path A, and that is a consequence of ADR-0005.** Motion
removes transforms two ways depending on the phase:

- `updateSnapshot()` → `measure()` → `removeTransform = true` → numeric removal via
  `removeTransform()` walking the path (`:1113`), *because the snapshot is taken in the
  pre-mutation phase where a DOM reset isn't available.*
- `updateLayout()` → `measure(false)` → no numeric removal, because the DOM was reset.

Wardic's retained Measurement is always produced by a measure pass — i.e. always in a
reset-capable phase. **So Wardic never needs Path B (numeric transform removal) at all.**
That is a genuine, under-recorded *benefit* of the retained-Measurement choice: it deletes
`removeTransform` / `removeBoxTransforms` and, as §8.7 shows, `resetSkewAndRotation` too.
The one caveat: any measurement taken *outside* a reset pass (e.g. a drag handoff reading a
live box) must be routed through the reset pass, or it reacquires the Path-B problem.

**Suggested fix shape** (Motion's three passes, adapted):

```
runMeasurePass():
  computeTree()                                    # already done, keep first
  ordered = nodes sorted by depth asc              # already done, keep

  # NEW: pass 1 — flag
  for node in ordered: for a in ancestorPath(node): a.shouldResetTransform = true

  # NEW: pass 2 — WRITE (no reads)
  for node in ordered: if node.shouldResetTransform or node.dirty:
      node.savedTransform = node.element.style.transform
      node.element.style.transform = ""            # clears translate/scale/rotate/skew alike

  # pass 3 — READ (no writes, no restores)
  documentScroll = measureDocumentScroll()
  for node in ordered: node.viewportBox = measureRect(node.element)   # raw getBoundingClientRect
                       if node.isScroll: sample scroll

  # pass 4 — WRITE (the existing body of the current loop, minus the measure)
  for node in ordered: foldScroll; retained/origin/layoutBox; spring seed; …

  deriveAll()          # already the write pass — now also the restore, since
  ensureRunning()      # writeProjection re-derives the transform from scratch
```

Note pass 4 + `deriveAll()` **is** the restore: `writeProjection` rebuilds the inline
transform from the new delta, so `savedTransform` only needs writing back for a node that
`deriveAll` won't touch (a node with no projection). Worth checking whether any such node
can be reset — if `shouldResetTransform` is only ever set on nodes in a dirty node's path,
and every such node is projection-owned, no explicit restore is needed. **But the restore
must land in the same synchronous pass, not on the next `Clock` tick** — see §8.3.

**Test shape:** the regression needs a *nested* mid-animation interrupt in real Chromium —
start a parent layout animation, and mid-flight trigger a child layout change; assert the
child's measured box matches its untransformed layout box. Confirmed: happy-dom cannot
catch this (`getBoundingClientRect` is zeroed), so it belongs in `test:browser`. A second
case worth covering, which only (b) exposes: **two sibling-chain nodes at different depths
measured in the same pass while the ancestor is mid-animation** — with the current
interleaved loop the deeper one is always wrong, regardless of scope. Motion's equivalent
fixtures are `dev/html/public/projection/animate-relative-interrupt.html` and
`animate-relative-nested-deep.html` — worth reading before writing Wardic's.

**Also port Motion's own falsifying fixture for the batching invariant.**
[PR #3748](https://github.com/motiondivision/motion/pull/3748) names
`parallel-calls-intersecting.html` and states its discriminating power precisely: *"call A's
update flow-pushes call B's element; **only pre-mutation batched snapshots give B the correct
origin**"* — and *"the first two fail against the previous implementation; all 27 pass
against this one."* A test with a stated pass/fail split against a known-broken
implementation is exactly what Wardic's regression needs, and the fixture is readable at
`dev/html/public/animate-layout/parallel-calls-intersecting.html` in the clone.

### 8.2 ADR-0005 — reframe the rejection, and add the explicit-boundary escape hatch

ADR-0005 rejects *"React-style synchronous pre-mutation snapshot for FLIP"* on the grounds
that *"Solid's push-based reactivity has no natural pre-commit hook; emulating one is
fragile."* That reasoning holds and should stand, but the ADR should be sharpened on two
points:

1. **Name what React actually provides.** It is not `useLayoutEffect`. It is
   `getSnapshotBeforeUpdate`, and Motion keeps a class component alive solely to reach it
   (`packages/framer-motion/src/motion/index.tsx:94-97`). The guarantee is a *tree-wide*
   pre-mutation barrier for the whole committing subtree. Solid's gap is not "no
   pre-mutation moment" but "no *singular, tree-wide* pre-mutation moment" — `createRenderEffect`
   gives per-node pre-mutation moments interleaved with writes, which is worse than none
   because it looks usable.
2. **Record what the trade actually costs**: trigger coverage, not timing. And record that
   **Motion itself ships both models** — retained Measurement as a documented fallback
   (`ensureDraggedNodesSnapshotted`, `create-projection-node.ts:2351-2362`, literally
   `node.snapshot = node.layout`) and an explicit caller-declared boundary for non-React
   (`LayoutAnimationBuilder` / `animateLayout`, [PR #3748](https://github.com/motiondivision/motion/pull/3748)).
   An `animateLayout`-shaped opt-in for Wardic would close the I1 gap exactly, with
   primary-source precedent, and is additive.
3. **Quote the counter-evidence.** Matt Perry considered post-mutation measurement in 2019
   and rejected it in the same thread — *"the auto measurements will be off as they'll all
   take place after the content is switched"*
   ([#275](https://github.com/motiondivision/motion/issues/275#issuecomment-525295014)) — and
   Motion's React-Compiler bug ([#3416](https://github.com/motiondivision/motion/issues/3416))
   is the modern demonstration of what a non-universal trigger costs. An ADR that records
   the strongest argument against its own decision is more useful than one that doesn't;
   the decision can still stand on "Solid gives us no tree-wide pre-mutation barrier",
   with `layoutDependency` + an explicit boundary as the mitigations.

### 8.3 ADR-0006/0009 — the measure pass runs on rAF, which is the option Motion rejected. **Second HIGH finding.**

ADR-0009 rejects "Gate owns projection timing" so that `TestClock` drives projection. That
is right for **Cycle B** (per-frame target/projection resolution) and the `TestClock`
argument is sound. But Motion's **Cycle A** (the commit: reset → measure → delta) runs on a
`queueMicrotask` batcher and then *synchronously drives one Cycle B + Cycle C pass out of
it* — precisely to avoid a paint:

> *"Manually flush any pending updates. Ideally we could leave this to the following
> `requestAnimationFrame` but this seems to leave a flash of incorrectly styled content."*
> — `create-projection-node.ts:794-798`

**Wardic's gate is rAF-based.** `makeFlushGate`'s own documentation
(`wardic:packages/solid/src/gate.ts:22-23, 78-84`):

> *"GATED rAF: a `write` schedules the rAF only if one is not already pending…"*
> *"Enqueue a pre-flush MEASURE pass (ADR-0009 / D4 — the projection read phase). The pass
> runs inside the next rAF BEFORE the write flush (reads-before-writes, one rAF), so it may
> read layout (`getBoundingClientRect`) and `write()` seed values that flush in the SAME
> frame."*

The reads-before-writes-in-one-rAF part is right and matches Motion's intra-pass structure.
The concern is the hop *into* the rAF. The sequence is:

```
Solid mutates the DOM (new layout live, no projection transform yet)
  → trigger fires → sink.scheduleMeasure(measurePass) → rAF pending
  → ??? possible paint ???
  → rAF: measure, seed FLIP at progress 0, write   ← element snaps back to its origin
```

If a paint lands at `???`, the user sees one frame of the element **at its destination**
before it jumps back to the origin and animates — the exact artifact Motion's comment
names.

**Whether that paint happens depends on the trigger, and I could not resolve it from a
primary source in this pass — flag as an open question, but a cheaply-answered one:**

- A `layoutDependency` / `notify` trigger firing from a Solid effect (i.e. in the task or a
  microtask) should schedule an rAF that runs in the *same* rendering cycle, before paint —
  safe.
- A `ResizeObserver` trigger is the risk: if resize-observer delivery happens *after* the
  frame's animation-frame callbacks in the HTML "update the rendering" steps, its
  `scheduleMeasure` lands on the **next** frame's rAF, with a paint in between. I attempted
  to verify this ordering against `html.spec.whatwg.org` ("update the rendering") and
  `drafts.csswg.org/resize-observer/` and **could not** — the resize-observer spec only says
  its algorithms *"are invoked as a part of update the rendering in the html spec"* without
  fixing their position relative to rAF callbacks.

**Recommended next step:** settle it empirically in the existing browser harness rather than
from spec archaeology — a `ResizeObserver`-triggered layout change, sampling
`element.getBoundingClientRect()` (or a paint-timing marker) on each frame, asserting the
element is never observed at its destination box before the animation starts. If it
reproduces, the fix is to route the commit through a microtask (Motion's
`microtask.read` + synchronous frame flush) rather than the gate's rAF — which does **not**
require moving Cycle B off the Clock, so ADR-0009's `TestClock` decision survives intact.

Motion's two-batcher design is the clean pattern for having both without two schedulers:
`frameloop/frame.ts` (rAF) and `frameloop/microtask.ts` (`queueMicrotask`) are *the same*
`createRenderBatcher` over *the same* eight ordered steps, differing only in
`scheduleNextBatch` and `allowKeepAlive`. Wardic's gate could grow a microtask-scheduled
sibling pass the same way.

### 8.4 ADR-0010 — check the crossfade easing windows and the `source` test

- The crossfade is **asymmetric**: lead fades in over progress `0→0.5` with `circOut`,
  follower fades out over `0.5→0.95` linearly
  (`projection/animation/mix-values.ts`, `easeCrossfadeIn`/`easeCrossfadeOut` via
  `compress`). If Wardic uses a symmetric cross-dissolve, the midpoint will look muddier
  than Motion's.
- Two opacity channels, not one: `opacity` (lead) and `opacityExit` (followers), selected in
  `applyProjectionStyles` (`:2055-2085`), with `preserveOpacity` as an override.
- Switch vs. Crossfade is decided by `Measurements.source` identity
  (`snapshot.source !== layout.source`, `:1610-1612`) — confirm Wardic's Measurement carries
  a producing-node id.
- Nested crossfades are explicitly blocked: `!this.path.some(hasOpacityCrossfade)` (`:1620`).
- Followers get `pointerEvents: "none"` (`:2130-2138`).
- `LayoutAnimationBuilder`'s **additions-before-removals-globally** rule is the non-React
  precedent for Wardic's leaving-Follower handling.

### 8.5 ADR-0011 — two divergences worth a decision

1. **`filter` is not corrected by Motion.** The registry is exactly
   `borderRadius` + 4 corners + `boxShadow` (`projection/styles/scale-correction.ts`).
   If Wardic corrects `filter`, that's a deliberate extension.
2. **`correctBorderRadius` emits a two-axis percentage (`X% Y%`) of `node.target`**, not
   `radius / scale`. Motion's stated reason is paint avoidance (*"If we animate between the
   two in percentage we'll avoid a paint"*) — and it is additionally exact under non-uniform
   scale, which a single division is not. ADR-0011's phrasing ("a px radius becomes
   `radius / scale`") should either be corrected or justified as a divergence.
3. Motion's corrector node interface is deliberately narrow — `{ target?, treeScale?,
   projectionDelta? }` — to avoid a circular import (`projection/styles/types.ts`). Good
   seam to copy. Note `correctBoxShadow` uses `projectionDelta.scale * treeScale`, and
   correction is skipped when `transform === "none"`.
4. Motion applies correctors by iterating **the registry**, passing **`lead`** (not `this`).

### 8.6 ADR-0012 / ADR-0013 — confirmed parity, one detail to check

- Scroll is sampled with a `phase` discriminator: `updateScroll(phase: "snapshot" | "measure")`
  (`:942`), cached per `(root.animationId, phase)`. So a node's scroll is sampled **twice per
  update** — once at snapshot, once at measure — and re-sampling is skipped within a phase.
  ADR-0012 says "sampled at measure"; Motion samples at both boundaries, and
  `ScrollMeasurements.wasRoot` tracks scroll-root transitions across them. Worth checking
  Wardic's `measureScroll` caching against this.
- The page-relative choice was a deliberate fix, not an accident. Matt Perry on the 2021
  rewrite ([#1159](https://github.com/motiondivision/motion/issues/1159#issuecomment-869846194)):
  *"One thing that was causing issues was the logic around the rebasing as **different parts
  of the tree were using measurements based on the viewport being in different places.** This
  has all been removed now in favour of **page-relative measurements** so many paths are
  simplified."* ADR-0012's scroll-stable frame is the same conclusion, independently reached —
  worth citing in the ADR as corroboration.
- `layoutRoot`'s four orchestration effects are listed in §2 above; `mixTargetDelta(1000)` at
  seed time (i.e. start settled) is the one most likely to be missing. **The source reading
  is confirmed by the PR that introduced it**
  ([#1781](https://github.com/motiondivision/motion/pull/1781), Matt Perry's own words):
  *"When applied to an element, it gets **forced to perform an instant layout animation any
  time a child performs one.** Then, any children can hook into its final layout to resolve
  relative layout animations."* — with the caveat, in the same PR, *"A more universal fix for
  this class of animations would be preferable but this will do for a quick fix"*, and later
  *"I don't like the API as it stands"*
  ([#1535](https://github.com/motiondivision/motion/issues/1535)). **`layoutRoot` is not
  settled upstream design** — worth knowing before Wardic commits to API parity. The
  alternative he rejected was walking ancestors with `getComputedStyle`, on cost grounds.
- `layoutAnchor === false` opts out of relative projection entirely, checked in two places
  (`:1243`, `:1314`) — consistent with ADR-0013.

### 8.7 `resetSkewAndRotation` — Motion needs it, Wardic does not. **No action.**

`startUpdate()` runs `nodes.forEach(resetSkewAndRotation)` tree-wide *before* any snapshot
(`:642-649`, implementation `:1919`). It zeroes `z`/`rotate*`/`skew*`, renders
**synchronously**, measures, then restores the values and `scheduleRender()`s. Rationale:
`getBoundingClientRect` on a rotated element returns the axis-aligned hull of the rotated
shape, which no translate+scale delta can invert. Unlike the projection-transform reset,
this one *does* save and restore individual values (`resetDistortingTransform`, `:94-109`).

**Why Motion needs a separate pass and Wardic doesn't.** Motion's snapshot phase can't
touch the DOM, so it removes transforms *numerically* (`removeBoxTransforms`) — and
rotate/skew are not numerically removable. Hence a dedicated DOM-level zeroing pass, run
early, for those keys only.

Wardic clears the **whole inline `transform` string** (`el.style.transform = ""`), and
`rotate`/`skew` are woven into that same string
(`wardic:packages/dom/src/renderer.ts:145-160`, the projection transform list). So once
§8.1's tree-wide reset pass exists, rotate and skew are cleared by it for free, on the node
*and* on every ancestor. **Verified: there is no rotate/skew-specific handling in
`packages/dom/src/projection.ts`, and none is needed.** Record this in ADR-0005 as a second
consequence of the retained-Measurement model, alongside the Path-B deletion in §8.1.

### 8.8 Other transferable details

- **Two boxes per Measurement** (`measuredBox` raw, `layoutBox` scroll+transform-free) plus
  a `source` node id. **Wardic's `NodeState` has neither split** — it keeps one
  scroll-folded `retained`/`layoutBox` (`wardic:packages/dom/src/projection.ts:218-245`) and
  decides Switch-vs-Crossfade structurally via `priorLeadOf(node)` + `seedOrigin()` rather
  than by comparing a `source` id. That looks like a legitimate simplification rather than a
  gap: Motion needs `measuredBox` mainly for the shared-transition `visualDelta`
  (`notifyLayoutUpdate`, `create-projection-node.ts:2188-2199`, where `isShared` uses
  `applyTransform(measuredLayout, true)` against `snapshot.measuredBox`). **Worth a
  deliberate check** that Wardic's crossfade delta is computed in the same space; if it
  isn't, the symptom is a shared-element animation that starts from a slightly wrong box
  when either twin carries a user transform.
- **Resize blocks rather than triggers**: on a `window.innerWidth` change Motion sets
  `updateBlockedByResize`, finishes all animations, and unblocks after 250 ms — but keeps
  measuring (`forceLayoutMeasure`) so `onLayoutMeasure`/`Reorder` consumers still work
  (`:461-487`, `:734-752`).
- **Safari-only box rounding**: `roundPoint` is `Math.round` on WebKit-not-Chrome and `noop`
  elsewhere — *"Measured bounding boxes must be rounded in Safari and left untouched in
  Chrome, otherwise non-integer layouts within scaled-up elements can appear to jump"*
  (`:2437-2447`).
- **`treeScale` snapping**: `applyTreeDeltas` snaps `treeScale` back to exactly `1` within
  `[0.999999999999, 1.0000000000001]` — *"This will help reduce useless scales getting
  rendered"* (`geometry/delta-apply.ts:67-68`, `:131-140`).
- **Render gating**: `calcProjection` only calls `scheduleRender()` when `treeScale` *or*
  either axis delta actually changed (`axisDeltaEquals` against `prevProjectionDelta`,
  `:1526-1544`). Idle projected nodes cost nothing.
- **`display: contents` is skipped** in `applyTreeDeltas` (`geometry/delta-apply.ts:100-110`),
  with a TODO wishing it away.
- **`resolvedRelativeTargetAt === frameData.timestamp`** is used as a same-frame memo, and
  `forceRelativeParentToResolveTarget()` (`:1169`) recursively forces ancestors — Motion
  calls it *"an unfortunate de-optimisation"*. Relevant if Wardic sees redundant work in
  relative chains.
